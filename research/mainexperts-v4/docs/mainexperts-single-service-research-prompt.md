**Версия 1.0 · готов к запуску на P01**

Скопируй документ целиком в новый рабочий чат. Чтобы исследовать другую точку, измени `SERVICE_ID` в параметрах и определи её границы из реестров. Раздел «Границы P01» применяется только к P01.

## 1. Задача и критерий результата

Выполни исследование одной точки CJM MainExperts. Найди все исследованные проекты, у которых исходные поисковые данные содержат запросы, относящиеся к этой точке. Для каждого установи, какая формулировка связана с какой страницей в исходной выгрузке, как интерфейс отвечает на запрос, что можно получить бесплатно и как проект переводит пользователя к следующей задаче, заявке, записи или оплате.

Покажи три масштаба анализа. Первый — каждая исходная формулировка со своей строкой и источником. Второй — кластер целиком с вариантами намерения, языками и рынками. Третий — каждый проект с посадочными, интерфейсом, снимками и исходом пути. По каждому утверждению о монетизации должна быть доступна проверка по экрану и URL. Отдельно опиши проекты, которые уверенно закрывают задачу, бесплатно переводят на следующий шаг, монетизируют смежный результат, имеют только упоминание в контенте или остались недоступны для проверки.

Результат — готовые файлы с доказательствами. Рабочие журналы используй для продолжения длинного прогона. Заверши работу результатами, фактическим покрытием и списком конкретных препятствий.

## 2. Источники и подготовка базы

1. Возьми комплект MainExperts v4.0, словарь кодов и CJM v4. Прочитай выбранную точку по `services.tsv`, `tasks.tsv`, `cluster_catalog.tsv`, `conversions.tsv` и `journey-v4-links.yaml`. Используй официальные источники и публичные страницы проектов для интерфейсной проверки.
2. Возьми готовый DuckDB либо восстанови его из семи частей. В комплекте есть `08-pipeline.md`, `parquet-manifest.json` и `pipeline/export_parquet.py`. Сверь контрольные суммы архивов. Части базы — справочники, запросы, разметка, исходные наблюдения 1, 2, 3, 4.
3. Для аналитики используй `query_journey`, `query_labels`, `query_observation_keys`, `sources` и `source_sheets`. Связка с `query_observation_keys` по `query_id` восстанавливает все наблюдения по каждому запросу. В `query_journey` для одного ключа выбран один представительный источник. Для проверки присутствия всех проектов одного представительного источника недостаточно.
4. Если доступ к какой-либо части базы закрыт, проверь исходную папку исследования на Google Drive и доступные копии внутри проекта. Сводные CSV и примеры из XLSX используй для ориентира. Контроль исходного охвата v4.0 — 245 поисковых выгрузок в 14 папках. Число проектов устанавливается после объединения доменов по проверенной принадлежности. Полноту подтверждай только по обработанным исходным наблюдениям. Внешние сайты, найденные дополнительно, помечай как внешний материал. Для них не приписывай запросы из исходного корпуса.
5. Сохрани состояние прогона по проектам, страницам и маршрутам. Обрабатывай таблицы пакетно вне контекста модели. Для большого числа сайтов можно распределить независимые проверки между агентами. Каждый получает общий справочник кодов, единый критерий подтверждения и свой набор URL. Объедини их результаты по идентификаторам.

## 3. Границы выбранной точки

Для любой точки зафиксируй исходный код, ветвь Q, задачи, связанные продукты и состояния CJM, ожидаемый результат, доступный самостоятельный путь и условия покупки. Если в сводке и карте различаются срезы, укажи, какие фильтры и знаменатель использованы.

### Границы P01

**P01 — диагностика и образовательный маршрут.** Ветвь Q01, входное состояние J01 и возможный возврат из J09. R06 — гипотеза MainExperts «Диагностика с разбором маршрута». E10 — диагностическая проба. C-P01-F — бесплатный вход, C-P01-A — предложение после полезного результата, C-P01-C — вход по прямому коммерческому запросу. Эти коды задают ориентир исследования. Интерфейсы других проектов описывай по тому, что реально увидел.

| Стартовое семейство | Что искать | Признак результата |
|---|---|---|
| K001 · Q01.02 | Диагностика интересов, склонностей и способностей | Пользователь получает интерпретацию, профиль или основанные на ответах варианты |
| K002 · Q01.05 | Связь желаемой роли с образованием и индивидуальный маршрут | Указаны подходящие направления обучения и основания выбора |
| K003 · Q01.07 | Запасной маршрут после отказа или срыва исходного плана | Есть применимая альтернатива с понятным условием выбора |
| K137 · Q01.06 | Что делать дальше в своей образовательной ситуации | Определён ближайший шаг и условие его выполнения |

Проверь четыре семейства полностью и просмотри остальные задачи Q01 на возможные пропуски. Дополнительные формулировки ищи по языкам корпуса, аудитории, стадии и результату. Разделяй тест, интерпретацию, выбор направления, персональный план, запасной маршрут, запрос цены, специалиста и заказа. У каждого уточнения должен быть собственный код или явно описанное соответствие исходному кластеру. Отдельно показывай смежные P06, P19 и P21, если они помогают увидеть переход. Обычный каталог, отдельная строго карьерная справка, клинические тесты, выбор вуза без диагностики и поиск контакта без определённой задачи требуют отдельного статуса, а не автоматического включения в P01.

## 4. Полный сбор запросов и проектов

### 4.1. Семантика

1. Собери основную разметку по `SERVICE_ID`. Добавь кандидатов по основным и вторичным семействам из `query_labels`, конкретным задачам карты и собственному поиску пропусков в неразмеченном массиве. `secondary_clusters` хранит массив базовых K, а не полных кодов `Knnn-Ixx`. Уточняй намерение отдельно. Сохраняй происхождение каждой метки и правило включения.
2. Проведи расширяющий проход по оригинальным языкам и посадочным. В P01 используй как поисковые подсказки эквиваленты «профориентационный тест», «подбор профессии по интересам», «разбор результатов теста», «консультация по профориентации», «сколько стоит», «купить отчёт», «что делать дальше» и «запасной образовательный маршрут». Переводи смысл под местную систему. Пример, сочинённый при поиске, становится наблюдением только после нахождения точной исходной строки или пометки как отдельного внешнего наблюдения.
3. Для кандидата присвой статус `included`, `adjacent`, `excluded` или `needs_review` и короткое основание. Различай основное и вторичное соответствия. Разводи `SEARCH_MARKET`, `SOURCE_REGION`, `DESTINATION`, язык запроса и язык интерфейса. Включай все оригинальные формы, включая бренды и опечатки при доказанной связи. При неоднозначности сохраняй её.
4. Составь таблицу отдельных запросов и отдельную сводку по кластерам. Группируй во втором разрезе по семье, намерению, рынку, поисковику, языку и типу метрики. Публикуй полный список фраз в приложении. В отчёте показывай характерные формулировки и ссылку на полный список. Для каждого кластера укажи принцип его объединения, число уникальных ключей, число связей с проектами, распределение D и долю пропусков. Частотности публикуй по отдельным запросам с методикой и датой. Итоговую частотность выводи только для сопоставимой, явно описанной группы. Не суммируй повторные оценки одной фразы, разные движки, контексты неизвестной географии и разные типы метрик. При сомнении оставь число запросов и покомпонентные оценки.

### 4.2. Реестр всех проектов

1. Начни со всех файлов и доменов в `sources`. После выборки запросов подними по `query_id` все исходные позиции, сырые строки, координаты и URL из `query_observation_keys`. Программа должна читать данные полностью и возвращать все совпадения. Ограничивать число выдаваемых в отчёте примеров можно. Ограничивать машинный реестр исходных совпадений нельзя.
2. Создай отдельные поля для проекта, домена выгрузки, домена посадочной, наблюдающего источника и домена оплаты. Учитывай зеркала, поддомены, местные версии, подразделения, редиректы и внешние платёжные сервисы. Назначай общий `PROJECT_ID` только при проверенной принадлежности. Сохраняй перечень связанных доменов и основание объединения. При конфликте имени файла и URL сохрани оба, поставь статус «домен не установлен» и установи его дополнительной проверкой. Пары файлов с одинаковым SHA-256 оставь в журнале происхождения и не учитывай как независимое подтверждение.
3. Для каждого исследованного проекта или пока не объединённого домена зафиксируй один итоговый статус. «Кластер обнаружен, путь проверен», «кластер обнаружен, путь частично проверен», «кандидат требует проверки», «в доступных данных совпадений не найдено», «нет доступа к источнику или сайту». Укажи число просмотренных источников и совместимых запросов, количество посадочных и сценариев, основание для статуса. Сайты без совпадений оставь в реестре охвата. Для проектов с совпадениями обязательно открой все уникальные релевантные посадочные или документируй точную причину пропуска каждой.
4. Если десятки URL фактически ведут в один путь, сохрани все URL и проверенные редиректы, но снимки можно сделать один раз на подтверждённый общий сценарий. Отдельный сценарий требуется при различии языка, аудитории, исходного обещания, состава бесплатного результата, момента регистрации, цены, плательщика или маршрута покупки. Для каждого проекта, кластера, рынка и языка покажи, какой проверенный маршрут их действительно обслуживает. Сохрани связку с каждой отдельной исходной фразой через наблюдение. Указывай, если связь фразы с маршрутами подтверждается только кластером или косвенным отношением. Если маршруты не совпадают, сохрани раздельные строки.

## 5. Проверка интерфейса и скриншоты

Каждый сценарий начни с посадочной из наблюдения. Запиши исходный и конечный URL, язык, дату наблюдения выгрузки и текущую дату просмотра. При изменившейся странице покажи оба состояния, если доступно надёжное публичное свидетельство прежнего состояния. Внешний поиск и обход сайта применяй для проверки связи. Отличай точное попадание, другое намерение на той же странице, косвенную связь и старые данные. Позиция из выгрузки не доказывает переход реального человека.

Зафиксируй шаги в фактическом порядке. Для каждого укажи, что видит человек, что должен сделать, какой элемент и точный текст CTA показаны, какие данные запрашиваются, что он получает и куда ведёт нажатие.

| Что фиксировать | Доказательство |
|---|---|
| Первый экран или блок, отвечающий на запрос | Заголовок, обещание, оригинальный CTA, URL, снимок |
| Действие и условия доступа | Тест, анкета, форма, чат, запись. Момент запроса регистрации или контактов |
| Бесплатный результат | Видимый отчёт, рекомендации, список, вариант следующего шага либо место, где путь прерывается |
| Следующий шаг | Точный CTA, экран назначения, бесплатный переход, заявка, эксперт или партнёр |
| Платное предложение | Продавец, получатель средств, состав результата, доступная цена и валюта, периодичность, условия |
| Последний публично доступный экран | Страница оплаты, корзина, запись, заявка либо экран внешнего получателя. Зафиксируй, есть ли прямое оформление |

Снимай реальные страницы. Минимум по каждому различающемуся пути — вход, полезный результат или препятствие к нему, предложение и последний публичный шаг. Если несколько состояний помещены на одном экране, допустим один снимок с несколькими ссылками на него. Для динамической формы сделай отдельные кадры состояния до и после безопасного действия. Сохраняй оригинальный текст на скриншоте. Если выделяешь важную область, оставь также исходный кадр. В PDF вставь читаемый снимок или крупный фрагмент. В ZIP положи оригиналы PNG с идентификаторами и журналом.

Используй публичный режим и безопасные тестовые значения там, где форма их допускает без создания заказа или отправки заявки. Если шаг требует оплаты, отправки контактных данных, обязательной регистрации, принятия юридических условий, авторизации или контакта с менеджером, отметь точку остановки. До подтверждения заказа, платежа, передачи персональных данных или отправки формы не доходи. Не обходи ограничения доступа. Скрывай контактные, личные и платёжные данные на снимках. Если экран недоступен, приложи доступное свидетельство и опиши попытку, причину и что осталось неизвестно. Пустой слот скриншота обозначай явно.

### Статус монетизации

Присвой каждому маршруту один основной наблюдаемый исход. Дополнительные ветки опиши отдельными строками.

| Исход | Условие присвоения |
|---|---|
| Бесплатный результат | Пользователь получает заявленную ценность и видит открытое продолжение или завершение |
| Бесплатный вход, платный результат | Публичный экран показывает отдельный платный отчёт, разбор или иной следующий результат |
| Прямая покупка | Есть публичное предложение и доступный экран оформления, продавец и условия видимы |
| Запись или заявка | Есть запись, форма или передача менеджеру. Цена, факт оплаты и формат оформления могут оставаться неизвестны |
| Партнёрский переход | Виден внешний исполнитель или получатель. Отдельно укажи, известна ли модель дохода |
| Смежная продажа | Платят за другой результат после решения или упоминания исследуемой задачи |
| Публичный ответ или внешний сбор | Официальный маршрут. Укажи, кому принадлежит сервис и кто принимает сбор при наличии |
| Монетизация не обнаружена | Пройдены доступные релевантные ветки, платный переход не найден |
| Проверка ограничена | Зона доступа, сбой, география, авторизация или недостаток наблюдений с указанием барьера |

D0–D6 оставь для доказательности спроса. Наличие видимого тарифа и кнопки покупки относится к доказательству интерфейса. Факт оплаты, конверсия и прибыль подтверждаются собственными данными. При неизвестной цене пиши «не показана». При неизвестной комиссии пиши «не установлена».

## 6. Итоговые файлы и ключи

Создай один комплект `mainexperts-[SERVICE_ID]-research`. В отчёте показывай русский перевод ключевых примеров и интерфейсных фраз. В базе сохраняй строки без подмены оригинала. При превышении лимита строк Excel оставь полный нормализованный CSV или Parquet, а в Excel добавь полный реестр проектов и управленческие разрезы.

| Файл | Требуемое содержание |
|---|---|
| `report.md` и `report.pdf` | Границы точки, охват и исключения, карта кластеров, сравнительная матрица всех проектов с найденным соответствием, карточка на каждый проверенный маршрут, скриншоты, выводы о бесплатной ценности, следующем действии и монетизации |
| `research.xlsx` | Листы «Охват», «Проекты», «Кластеры», «Запросы», «Наблюдения», «Проекты × кластеры», «Маршруты», «Шаги и экраны», «Пробелы». Фильтры, стабильные ключи и проверенные ссылки |
| `data/` | Полные CSV или Parquet, таблица сопоставления запросов с кластерами и статусами, правила включения, журнал обработки и исходные идентификаторы |
| `screenshots/` | PNG с идентификаторами и `screenshots.csv`. Метаданные указывают проект, сценарий, шаг, URL, время, локаль, устройство, состояние доступа, файл и утверждение, которое подтверждает снимок |
| `evidence.zip` | Копии таблиц, отчётов, снимков и краткий README для воспроизведения. Ссылки внутри архива должны работать после распаковки |

Свяжи таблицы следующими ключами. Названия полей можешь расширить, сохраняя раздельные сущности.

| Таблица | Ключи и обязательные поля |
|---|---|
| `queries` | `QUERY_ID`, нормализованная форма, язык, рынок поиска, поисковик, страна назначения при наличии, D |
| `observations` | `OBSERVATION_ID`, `QUERY_ID`, `SOURCE_ID`, лист, номер строки, оригинальная фраза, домен источника, URL, частотность, CPC, KD, тип показателя и дата |
| `query_clusters` | `QUERY_ID`, `CLUSTER_ID`, намерение, основное или вторичное соответствие, правило, статус и исключение |
| `projects` и `project_clusters` | `PROJECT_ID`, домены, `CLUSTER_ID`, рыночный срез, число ключей и наблюдений, статусы проверки, ссылки на доказательства |
| `pathways` и `steps` | `PATH_ID`, `STEP_ID`, `PROJECT_ID`, кластер или связь с несколькими кластерами, фактический URL, элемент, точный CTA, условие, бесплатный результат, следующее действие, продукт, цена и получатель, статус наблюдения |
| `path_observations` | `PATH_ID`, `OBSERVATION_ID`, основание и уверенность связи. Эта таблица соединяет исходную фразу с реально наблюдённым маршрутом |
| `screenshots` и `gaps` | Идентификаторы, ссылки на шаг или источник, условия просмотра, путь к PNG или точная причина отсутствия, требуемое повторное действие |

В отчёте для каждого проекта дай короткое резюме в одном формате. **Что ищут → какой результат обещан → какой экран и CTA → что человек фактически получает → какой следующий шаг → где появляется цена или обращение → кто получает деньги.** Покажи лучшие паттерны отдельно для входов D1, D2 и D3. Для MainExperts предложи бесплатный результат, подходящий следующий CTA, условие показа платного предложения и вопрос, который нужно проверить экспериментом.

## 7. Приёмка и две критические проверки

1. **Охват и трассировка.** Сверь число файлов, доменов, проектов, запросов, кластеров, посадочных, маршрутов и снимков. У каждого исходного файла и проекта есть статус. Каждая включённая фраза ведёт до исходной записи. Каждое наблюдаемое решение ведёт до страницы и снимка либо до причины, почему доказательство недоступно. Проверь вторичные совпадения, все 14 папок при их доступности, неразмеченный массив, дубли, разные домены под одним брендом и рынки с пропущенной географией. Внутренний проход по одному источнику на запрос считать ошибкой.
2. **Предмет и коммерция.** Попробуй опровергнуть самые сильные выводы. Проверь, отвечает ли интерфейс нужному намерению, виден ли сам результат или только обещание, совпадают ли посадочная и запрос по объекту, действительно ли клик ведёт к найденному экрану, кто принимает оплату, можно ли пройти без менеджера, какие шаги скрыты за формой. Отдельно проверь, что цена относится к нужному результату, а не к обучению, подписке на другое предложение или внешнему сбору. Исправь найденное или зафиксируй непроверимый участок.
3. Пройди выборку сквозной проверки вручную по одному маршруту каждого наблюдаемого типа, рынкам с наибольшим объёмом и существенным исключениям. Открой сгенерированные PDF и XLSX, проверь читаемость, наличие снимков, целостность ссылок и проверяемые итоги. Сверь, что список причин пропуска даёт точную границу слова «все».

Заверши ответ ссылками на файлы, числом проектов в корпусе и с совпадениями, числом проверенных маршрутов и скриншотов, необработанными источниками и тремя предметными наблюдениями по выбранной точке. Не подменяй результат планом.

## Приложение. Стартовый запрос к DuckDB

Запусти выборку как базовый проход. Она возвращает основные совпадения, попадания по исходным семействам и вторичные соответствия вместе со всеми их наблюдениями. Перед дальнейшим анализом присвой кандидатам предметный статус и дополни расширяющим проходом из раздела 4. Для другого кода достаточно заменить значение в CTE `params`. Запиши результат в CSV или Parquet с помощью `COPY`.

```sql
WITH params AS (
  SELECT 'P01' AS service_id
), families AS (
  SELECT c.cluster_base_id
  FROM cluster_catalog c
  JOIN params p ON c.service_id = p.service_id
), candidates AS (
  SELECT l.query_id, l.cluster_base_id, l.cluster_id, l.intent_id,
         l.task_id, l.evidence_level, l.language, l.service_id,
         l.secondary_clusters,
         coalesce(l.service_id = p.service_id, false) AS direct_service,
         coalesce(l.cluster_base_id IN (
           SELECT cluster_base_id FROM families
         ), false) AS primary_family,
         EXISTS (
           SELECT 1 FROM families f
           WHERE list_contains(
             try_cast(l.secondary_clusters AS VARCHAR[]),
             f.cluster_base_id
           )
         ) AS secondary_family
  FROM query_labels l
  CROSS JOIN params p
)
SELECT c.*, o.query_raw, o.query_normalized, o.search_market,
       o.search_engine, o.source_region, o.source_id, o.sheet,
       o.row_no, o.source_url, s.nominal_domain, o.target_url,
       o.target_raw, o.volume, o.volume_metric, o.cpc, o.kd,
       o.position, o.observed_date, o.export_date, o.sha256
FROM candidates c
JOIN query_observation_keys o USING (query_id)
JOIN sources s USING (source_id)
WHERE c.direct_service OR c.primary_family OR c.secondary_family;
```

Для контроля покрытия сделай отдельный запрос от `sources` с левым соединением результатов по `source_id`. Так останутся видны исходные файлы с нулём подходящих наблюдений. Сравни количество уникальных `QUERY_ID` и количество исходных строк после объединения. Разница показывает, сколько связей с источниками потерялось бы при чтении только представительных наблюдений.
