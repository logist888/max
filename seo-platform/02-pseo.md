## 1. Региональная архитектура

Сравнение трёх подходов (по заданию):

| Критерий | Отдельные домены | Поддомены (msk.site.ru) | Подкаталоги (/gorod/moskva/) |
|---|---|---|---|
| Накопление ссылочного веса | распыляется по доменам | частично распыляется: поддомен для поисковиков близок к отдельному сайту | весь вес на одном хосте |
| Яндекс | нужен отдельный региональный хост и присвоение региона каждому | регион присваивается поддомену через Вебмастер — рабочая схема для гео-зависимых коммерческих запросов | один хост, гео-страницы ранжируются контентом; для информационно-выборных запросов достаточно |
| Google | дорого и бессмысленно | допустимо, но консолидация слабее | рекомендуемый по умолчанию путь |
| Стоимость поддержки | максимальная (SSL, аналитика, вебмастеры × N) | средняя (wildcard-SSL, N профилей в вебмастерах) | минимальная (один хост, одна аналитика) |
| Скорость запуска и краул | медленно: каждый хост индексируется с нуля | средне | быстро: новый раздел наследует доверие хоста |
| Аналитика и эксперименты | фрагментированы | склейка кросс-доменных визитов | сквозные из коробки |

**Выбор: подкаталоги.** Причины: (1) запросы платформы — выборные
(«вузы москвы», «куда поступать с информатикой»), а не локально-сервисные,
где поддоменная геопривязка Яндекса даёт решающее преимущество; (2) молодой
домен не может позволить себе распыление веса на 357 городов; (3) один хост —
одна аналитика и один вебмастер, что критично при малой команде (C8 ещё
не отвечен). Риск выбора: если через год гео-выдача Яндекса по коммерческим
запросам («поступить в вуз в {город}») окажется недосягаемой без
геопривязки — точечно выделяются 2–3 городских поддомена как эксперимент;
подкаталожная структура этому не мешает.

## 2. Инвентарь индексируемых страниц (из выгрузки)

| Тип | Условие включения | Штук на старте |
|---|---|---|
| Карточка вуза | все организации РФ | 1 785 |
| Регион | все с ≥1 вузом | 87 |
| Город | все с ≥1 вузом | 357 |
| Направление (ОКСО) | все встречающиеся | 894 |
| Группа УГСН (ступица) | все встречающиеся | 57 |
| Направление × город | **≥2 вузов** в комбинации | 4 317 |
| Направление × регион | ≥2 вузов **и ≥2 городов** | 1 987 |
| Кураторские фасетные посадочные | вручную из админки (правило ниже) | ~100–150 |
| Главная, каталоги, квиз, статьи | — | ~10 + редакция |
| **Итого канонических** | | **≈ 9 600** |

Обоснование порогов:

- **Направление × город при ≥2 вузах.** Страница с одним вузом не отвечает
  на запрос выбора («где учиться на X в Y») лучше, чем сама карточка вуза, —
  это дубль тонкого содержания и каннибализация карточки. Комбинаций с
  одним вузом — 16 248 из 20 565: порог отсекает 79% мусорного объёма.
  Спрос закрывается так: карточка вуза (единственного) собирает эти запросы
  своим содержимым, городская страница ссылается на неё.
- **Направление × регион только при ≥2 городах.** Если все вузы комбинации
  в одном городе, региональная страница дублирует городскую — на неё
  ставится canonical городской версии (таких 3 301). Уникальная ценность
  региональной — сравнение городов внутри субъекта (1 987 страниц).
- **Кураторские фасетные посадочные** («вузы с военной кафедрой в Москве»,
  «общежития для студентов в {город}», «стоимость обучения в {город}»).
  В базе: городов с ≥3 вузами с военной кафедрой — 9; с ≥5 вузами с
  общежитием — 38; с ≥5 вузами с известной стоимостью — 71. Массовая
  генерация запрещена: каждая включается вручную из админки (флаг у
  сохранённого фильтра) и требует редакционного вводного абзаца. Это
  держит фасетный слой на уровне сотни осмысленных страниц.
- **Города со единственным вузом (185) индексируются.** В отличие от
  комбинаций, городская страница — сущностная («вузы в {город}») и несёт
  уникальный локальный факт даже при одном вузе; она же — узел перелинковки
  на регион и соседей.

Проверка спроса: инструментов частотности в проекте нет, и цифры спроса в
этом документе не выдумываются. Порядок работы: включение по наполненности
(таблица выше) → после запуска ежемесячный пересмотр по фактическим
показам Вебмастера/Search Console → комбинации с нулевыми показами за
3 месяца уходят в noindex (адрес живёт), стабильно растущие фасеты —
кандидаты в кураторские посадочные.

## 3. Правила фасетной навигации

Фильтры каталога (уровень, форма, тип мест, стоимость, общежитие, военная
кафедра, наличие бюджетных мест) живут в параметрах запроса:

- Параметрические адреса: `meta noindex, follow` + canonical на базовую
  страницу раздела. В robots.txt параметры **не** закрываются — иначе
  поисковик не увидит noindex/canonical.
- Внутренние ссылки никогда не ведут на параметрические адреса — только на
  канонические страницы инвентаря. Фильтры применяются интерактивно.
- Кураторская посадочная = сохранённый фильтр, получивший постоянный
  человеческий адрес (`/vuzy/moskva/voennaya-kafedra/`), заголовок,
  вводный текст и место в перелинковке. Только такие адреса из фасетного
  слоя попадают в sitemap.
- Сортировки, вид списка, страница — служебные параметры, canonical
  их игнорирует.

Пагинация каталогов: страницы 2+ — `noindex, follow`, canonical на себя,
в sitemap не входят. Все сущности и так достижимы через sitemap и ступицы,
поэтому индекс не теряет ничего, а дубли заголовков исключаются. Альтернативы
(самоканонические индексируемые страницы N; canonical всех страниц на первую)
отклонены: первая плодит слабые дубли в индексе, вторая — некорректное
употребление canonical (страницы не эквивалентны), риски склейки у Яндекса.

## 4. Перелинковка «ступица и спицы»

Ступицы: направление, УГСН, город, регион. Спицы: комбинации и карточки.

- Карточка вуза → город, регион, головной/филиалы, до 10 направлений вуза
  (сгруппированы по УГСН, ссылки на «направление × город» при наличии),
  «вузы рядом» (тот же город, пересечение УГСН).
- Направление × город → ступицы (направление, город), карточки участников,
  «это направление в соседних крупных городах» (топ по числу вузов),
  «родственные направления в этом городе» (та же УГСН).
- Город → регион, все вузы города, направления города с ≥2 вузами,
  кураторские посадочные города.
- Хлебные крошки: Главная → Регион → Город → Вуз;
  Главная → Специальности → УГСН → Направление → Направление×город.
- Правило сирот: каждая каноническая страница достижима с главной за ≤3
  перехода по ссылкам; проверка автоматическая при пересборке витрин
  (страница без входящих внутренних ссылок = ошибка сборки, не заметка).

## 5. Автогенерация мета-слоя (только факты базы)

Шаблоны на тип страницы; переменные — из витрин; правило пропуска: нет
данных — фраза выпадает целиком, «Информация отсутствует» в мета-тексты
не пишется, на странице пробел показывается явно.

- Карточка вуза. Title: «{Короткое имя} — программы, стоимость, общежитие |
  {Город}». H1: полное имя. Description: собирается из фактов: число
  направлений (из списка программ — счётчик источника не публикуется до
  закрытия Д4), диапазон стоимости платных, наличие бюджетных мест, флаги
  общежития и военной кафедры. FAQ (только вопросы с ответом в данных):
  «Есть ли бюджетные места», «Сколько стоит платное обучение», «Есть ли
  общежитие/военная кафедра», «Какие уровни образования». JSON-LD:
  CollegeOrUniversity (имя, адрес, сайт) + BreadcrumbList + FAQPage.
- Направление × город. Title: «{Направление} в {город}: {N} вузов[, от
  {мин. стоимость} ₽/год]». ItemList вузов, BreadcrumbList, FAQ из
  агрегатов (сколько вузов, есть ли бюджет, вилка цен, формы обучения).
- Город/регион/направление/УГСН — аналогично из агрегатов.
- Главная: WebSite + SearchAction; Organization сайта.
- OpenGraph всюду: заголовок = Title без хвоста бренда, описание =
  Description, изображение — генерируемая карточка с фактами (без фото
  вузов — их в базе нет).
- Подпись данных на каждой странице с фактами: «Источник: данные
  „ВУЗ-навигатора“ Госуслуг, выгрузка от {дата снимка}» — требование
  этапа 1 (Р3) и опора E-E-A-T для YMYL-тематики. Плюс страница
  «/o-dannyh/» — что за данные, как обновляются, чего в них нет.

## 6. Жизненный цикл адресов

- Смена слага (переименование вуза) → 301, id в слаге держит связь.
- Вуз исчез из свежей выгрузки → страница живёт одну кампанию с плашкой
  «отсутствует в выгрузке от {дата}», затем 410. Слияние вузов → 301 на
  преемника (ручное решение при импорте).
- Комбинация упала ниже порога → noindex + исключение из sitemap и
  перелинковки; адрес отвечает 200 (вернётся — вернётся в индекс).
  Ниже одного вуза → 404 не отдаём, отдаём городскую ступицу через 302?
  Нет: адрес остаётся 200 с одним вузом и noindex — стабильность важнее
  экономии на горстке страниц.
- Sitemap: сегментированные карты по типам (vuzy, goroda, regiony,
  specialnosti, combo, кураторские, статьи) + индексная; lastmod — дата
  принятия снимка; только канонические индексируемые адреса.
- Краул-бюджет: ≈9,6 тыс. канонических адресов — на порядки ниже угрозы;
  единственный реальный риск (взрыв параметров) закрыт разделом 3.

## 7. Итог этапа

1. **Решение.** Подкаталоги; инвентарь ≈9,6 тыс. канонических страниц с
   порогами «≥2 вузов» (город-комбо) и «≥2 вузов + ≥2 городов»
   (регион-комбо); фасеты noindex с ручным кураторским слоем; пагинация
   noindex,follow; мета-слой генерируется только из фактов; жизненный цикл
   301/410/noindex определён.
2. **Альтернативы.** Региональность: домены/поддомены/подкаталоги (раздел 1).
   Пороги: без порога (20,5 тыс. комбо) — отклонено как фабрика тонких
   дублей; порог ≥3 (1 763 комбо) — отклонено: режет живые страницы
   двухвузовых городов; ≥2 — выбран. Пагинация: три схемы (раздел 3).
3. **Причины выбора.** Консолидация веса молодого домена; пороги посчитаны
   из фактической наполненности выгрузки; отказ от выдуманных цифр спроса
   в пользу цикла «включили по наполненности → пересмотрели по показам».
4. **Риски.** Гео-выдача Яндекса может потребовать поддоменного
   эксперимента (путь отхода описан); спрос на комбо-страницы не
   подтверждён инструментально до запуска; кураторский слой зависит от
   редакционного ресурса (C8).
5. **Ограничения.** Ни одна страница не генерируется без данных; мета-слой
   не содержит выдуманных цифр; счётчик источника не публикуется (Д4).
6. **Критерии качества.** Каждый канонический адрес: в sitemap, достижим
   за ≤3 перехода, имеет уникальный Title/H1/Description из фактов, отдаёт
   корректный JSON-LD; ни один параметрический адрес не в индексе.
7. **Checklist готовности.** [x] Три региональные схемы сравнены.
   [x] Инвентарь посчитан из выгрузки (`seo-platform/inventory.py`;
   канонический инвентарь без кураторского и редакционного слоёв — 9 484).
   [x] Пороги обоснованы цифрами. [x] Правила фасетов,
   пагинации, canonical, sitemap, 301/410 заданы. [x] Шаблоны мета-слоя
   определены. [ ] Подтверждение владельца → этап 3 «Поиск».

**Этап 3 (после подтверждения):** поиск — движок, морфология русского,
аббревиатуры («МГУ» = «Московский государственный университет» = «MSU»),
опечатки, ранжирование (название > направление > город > статья),
мгновенная выдача, целевая скорость.
