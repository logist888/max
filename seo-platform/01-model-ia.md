## 1. Решения владельца, зафиксированные 11.07.2026

**Р1. «Режем то, что не знаем».** Из объёма исключаются все разделы без
данных в базе:

| Вырезано | Причина | Слот на будущее |
|---|---|---|
| /ege/, комбинации «ЕГЭ + специальность» | нет предметов ЕГЭ | да — при появлении источника |
| проходные баллы, калькуляторы баллов | нет баллов | да |
| /professiya/ | нет онтологии профессий | да |
| факультеты, кафедры | нет структуры вузов | да |
| рейтинги, отзывы, зарплаты, востребованность | нет данных, выдумывать запрещено | да |

Слот означает: модель данных и карта разделов оставляют место под сущность,
но ни одна страница не создаётся и ни одна ссылка на неё не ставится.

**Р2. Конверсионная точка — настраиваемая.** Требование: владелец в любой
момент направляет трафик на любую страницу любого сайта, вписав адрес.
Проектное следствие — **реестр конверсионных целей** в административной
панели, а не зашитые ссылки:

- Сущность «цель»: код, название, адрес (любой URL), шаблон UTM-меток,
  признак активности.
- Сущность «размещение»: тип страницы × зона (карточка вуза / список /
  статья / квиз / закреплённая кнопка) → активная цель. Смена точки —
  правка одной записи, без выкладки кода.
- Честная метрика: на нашей стороне достоверно измеряется **клик по цели**
  (и весь путь до него); сам факт покупки происходит на внешней стороне и
  виден только через UTM в аналитике принимающего сайта. North Star
  «оплаченные диагностики из органики» считается сквозной связкой
  «наш клик с меткой → покупка у приёмника»; без доступа к аналитике
  приёмника платформа отчитывается кликами по цели. Это ограничение
  фиксируется, не маскируется.

**Р3. Право публикации.** Решение владельца: данные «ВУЗ-навигатора»
публичные, запрета на публикацию нет. Фиксируется как решение от 11.07.2026.
Остаточная практика (и польза для доверия к YMYL-сайту): на каждой странице
с данными указывать источник и дату актуальности выгрузки.

Открытыми из этапа 0 остаются: C8 (бюджет, сопровождение, предпочтения по
стеку — нужен к этапу «Технологии») и Д4 (семантика счётчика источника —
проверка на стороне парсера; до неё счётчик не публикуем).

## 2. Каноническая модель данных

### 2.1 Сравнение вариантов

**В1. Документная модель «как есть»**: хранить JSON выгрузки, один документ —
вуз, страницы читают документ напрямую.
Плюсы: нулевая стоимость импорта; полное соответствие источнику.
Минусы: города и направления не сущности — нет страниц /gorod/ и
/specialnost/ без дублирующей логики; агрегации (счётчики, диапазоны цен)
считаются на лету; нормализация городов размазывается по коду; история
изменений — только целыми документами.
Стоимость сопровождения: низкая вначале, растёт с каждым новым типом страниц.

**В2. Полная нормализация (3НФ)**: организации, филиалы, регионы, города,
направления, группы направлений, программы-конкурсы, справочники уровней,
форм и типов мест — отдельные отношения; страницы читают соединения.
Плюсы: единственный источник каждого факта; целостность по ключам; страницы
любой сущности — естественны; история точечная.
Минусы: каждая страница каталога — многотабличное соединение под нагрузкой;
для SEO-сайта, где чтения на порядки больше записей (импорт — раз в
недели), плата за соединения постоянная, а выгода от строгой записи
почти не используется.
Стоимость сопровождения: средняя; схема жёсткая, миграции дисциплинируют.

**В3. Гибрид: нормализованное ядро + витрины чтения.** Ядро — как В2
(истина, импорт, история); поверх — денормализованные витрины, собираемые
после каждого импорта: «карточка вуза» (весь состав одной записью),
«строка каталога», «агрегаты города/региона/направления» (счётчики,
диапазоны стоимости, списки уровней), поисковый индекс.
Плюсы: страницы читают одну плоскую запись — скорость и простота шаблонов;
истина остаётся нормализованной — импорт, проверки и история строгие;
витрины пересобираются целиком — нет рассинхронизации.
Минусы: две схемы вместо одной; витрины надо пересобирать дисциплинированно
(шаг конвейера импорта, не ручная операция).
Стоимость сопровождения: средняя; сложность локализована в одном шаге сборки.

**Выбор: В3.** Причина: профиль нагрузки SEO-платформы — массовое чтение
однотипных страниц при редком пакетном обновлении из одного источника.
Это ровно случай «строгая истина + плоские витрины». В1 отвергнут из-за
отсутствия сущностей для ключевых типов страниц, В2 — из-за постоянной
платы за соединения там, где хватает пересборки витрин раз в импорт.

### 2.2 Сущности ядра

Идентификаторы источника сохраняются всюду (id «ВУЗ-навигатора» — ключ
сверки между выгрузками).

- **source_snapshot** — выгрузка: имя файла, sha256, размер, дата парсинга,
  итоги проверки (число организаций, записей программ, пропусков). Каждая
  загрузка проходит `audit_json.py` как входной контракт; провал контракта —
  выгрузка не принимается.
- **organization** — вуз или филиал: id источника, три названия, тип
  (головной / филиал / зарубежный филиал), ссылка на головной (`parent_id`,
  допускает пустоту — заполняется эвристикой по названию и ручной курацией,
  начиная с крупнейших), город, адрес, контакты, сайты, флаги военной
  кафедры и общежития, места в общежитии (допускает пустоту), полезные
  ссылки источника (24 вида, все допускают пустоту).
- **region** (88) и **city** (~375) — нормализованные справочники; у города —
  канонное имя, регион, список сырых написаний из источника (правило
  нормализации префиксов «г.», «пос.» и разночтений регистра — данные
  этапа 0, 53 группы).
- **direction** — направление/специальность: код ОКСО (894), название
  (в базе консистентно), группа УГСН.
- **ugs_group** — укрупнённая группа: двузначный код из ОКСО; названия — из
  официального перечня Минобрнауки (внешний нормативный справочник;
  подключается с источником, датой и ссылкой — единственное внешнее
  обогащение, разрешённое правилами).
- **program_offer** — конкурсная позиция: организация × направление ×
  уровень × форма × тип мест × год кампании; места, стоимость (0 у платных =
  «Информация отсутствует», не ноль). Дубли кортежа допустимы — это разные
  конкурсы источника; витрины агрегируют.
- **Справочники**: уровень (обе системы — действующая и пилот «базовое /
  специализированное высшее»; ординатура и ассистентура присутствуют как
  уровни-заглушки со статусом «не выгружается источником»), форма обучения,
  тип мест (6 значений, квоты).
- **admission_campaign** — год набора. В выгрузке год не указан; по дате
  парсинга (10.07.2026) принимается кампания 2026/27 — **допущение,
  подтвердить у парсера**; поле обязательно, чтобы следующая кампания легла
  рядом, а не поверх.
- **conversion_goal / cta_placement** — реестр целей и размещений (раздел 1, Р2).
- **article** — редакционный контур (слот: статьи-гайды воронки «понять
  себя»); структура задаётся на этапе карточек и конверсии.

История: импорт нового снимка не перезаписывает старый — витрины собираются
из «текущего принятого снимка», прежние остаются для сравнения (что
появилось/пропало/подорожало — это же сырьё для будущих страниц «изменения»).

### 2.3 Витрины чтения (пересборка после каждого импорта)

- «Карточка вуза»: организация + её программы, сгруппированные по уровню и
  группе УГСН, агрегаты (число направлений — **считается из списка программ**,
  счётчик источника не публикуется до закрытия Д4), диапазоны стоимости,
  филиалы/головной.
- «Строка каталога»: всё для списков и фильтров без соединений.
- «Агрегаты географии»: город/регион → вузы, направления, диапазоны
  стоимости, счётчики для заголовков и текстов страниц.
- «Агрегаты направления»: направление → вузы, города, уровни, стоимость.
- Поисковый индекс (проектируется на этапе «Поиск»).

## 3. Информационная архитектура

Только разделы, обеспеченные данными. Решения об индексации каждого типа —
на этапе 2 (Programmatic SEO и фасеты); здесь — предварительная разметка.

| Раздел | Шаблон адреса | Данные | Индексация (предв.) |
|---|---|---|---|
| Главная | / | витрины | да |
| Каталог вузов | /vuzy/ | строки каталога | да |
| Карточка вуза | /vuz/{слаг}/ | карточка | да |
| Регионы | /regiony/, /region/{слаг}/ | агрегаты | да |
| Города | /gorod/{слаг}/ | агрегаты | да (при ≥1 вузе) |
| Направления | /specialnosti/, /specialnost/{слаг}/ | агрегаты | да |
| Группы УГСН | /specialnosti/{группа}/ | агрегаты | да |
| Комбинация «направление в городе» | /specialnost/{слаг}/{город}/ | агрегаты | решается этапом 2 (порог спроса и наполненности) |
| Фильтры каталога (стоимость, общежитие, военная кафедра, уровень, форма) | параметры запроса | строки каталога | нет (кроме выделенных этапом 2 посадочных) |
| Сравнение вузов | /sravnenie/ | карточки | нет |
| Поиск | /poisk/ | индекс | нет |
| Статьи | /articles/… (слот) | редакция | да |
| Квиз «понять себя» | /test/ (мост к цели) | реестр целей | да (одна страница) |
| Избранное | локально в браузере | — | нет |

Принципы, уже принятые здесь (не откладываются до этапа 2):

- **Зарубежные филиалы** (28): страницы не создаются, на карточке головного
  вуза упоминаются списком (Д5 закрыт продуктово).
- **Вузы без программ** (9 ординатурных медцентров): карточка существует,
  честно сообщает «программы этого уровня источником не выгружаются»;
  из каталожных списков по направлениям они исключены.
- **Персональные данные**: избранное и сравнение — в браузере пользователя,
  без учётных записей. Аудитория несовершеннолетняя — платформа на этом
  этапе не собирает ПДн вообще; личный кабинет не строится, пока не
  определена точка конверсии с той стороны (снимает вопрос B7 этапа 0).
- Терминология адресов: единый префикс «specialnost» для направлений всех
  уровней (в народном языке запроса доминирует «специальность»; уровень —
  свойство страницы, не адреса).

### 3.1 Слаги: сравнение и выбор

В1 — чистая транслитерация («/vuz/mgu/»): красиво, но короткие имена
неуникальны (три «МГУ» в базе) и меняются при переименованиях.
В2 — только id источника («/vuz/3089/»): устойчиво, но адрес не несёт слов —
хуже для сниппета и кликабельности.
В3 — транслитерация + id («/vuz/donnasa-filial-niu-mgsu-3089/»): читаемо,
гарантированно уникально, переименование не ломает адрес (слаг обновляется
с перенаправлением 301, id держит связь).
**Выбор: В3** для вузов; для направлений — код ОКСО в слаге
(«/specialnost/09-03-01-informatika/»), для городов и регионов — чистая
транслитерация (они уникальны после нормализации).

## 4. Итог этапа (по порядку работы задания)

1. **Решение.** Гибридная модель «нормализованное ядро + витрины чтения»;
   ИА из 12 разделов строго на данных базы; реестр настраиваемых
   конверсионных целей; слаги «транслит + id».
2. **Альтернативы.** Модель: документная / 3НФ / гибрид (2.1). Слаги: три
   варианта (3.1). Конверсия: зашитая ссылка / реестр целей — выбран реестр
   по требованию Р2.
3. **Причины выбора.** Профиль нагрузки «массовое чтение, редкий пакетный
   импорт»; требование владельца менять точку конверсии без выкладки;
   уникальность и устойчивость адресов.
4. **Риски.** Год кампании — допущение (подтвердить); связь филиал→головной
   заполняется постепенно (до заполнения карточки филиалов живут без
   ссылки на головной); покупка видна только через аналитику приёмника;
   Д4 не закрыт — счётчик источника не публикуем.
5. **Ограничения.** Никаких страниц без данных; пропуск = «Информация
   отсутствует»; внешнее обогащение — только перечень УГСН с реквизитами.
6. **Критерии качества.** Каждая сущность ядра прослеживается до поля
   выгрузки; каждый раздел ИА — до витрины; ни один адрес не ведёт на
   пустую страницу; импорт защищён входным контрактом `audit_json.py`.
7. **Checklist готовности.** [x] Решения владельца зафиксированы.
   [x] Три варианта модели сравнены, выбор обоснован. [x] Сущности ядра и
   витрины описаны. [x] Карта разделов и правила слагов заданы.
   [ ] Подтверждение владельца → этап 2.

**Этап 2 (после подтверждения):** Programmatic SEO — какие комбинации
становятся посадочными страницами (пороги спроса и наполненности), правила
