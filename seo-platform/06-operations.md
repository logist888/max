# SEO-платформа — Этап 6: дизайн-система, производительность, аналитика, эксплуатация, безопасность, качество кода

> Дата: 11.07.2026. Этапы 0–5 подтверждены (стек этапа 5 — с допущением C8).
> Все требования здесь измеримы; субъективных формулировок нет.

---

## 1. Дизайн-система (закрывает раздел «UI» задания)

**Типографика.** Один переменный шрифт с полной кириллицей (класса Inter),
два файла woff2 (обычный, жирный) с подмножеством кириллица+латиница+цифры,
`font-display: swap`, предзагрузка. Базовый размер 16px, межстрочный 1.5;
модульная шкала 1.2: 13 / 16 / 19 / 23 / 28 / 33 / 40. Длина строки текста
60–75 знаков.

**Сетка.** 12 колонок, контейнер до 1280px, отступы кратны 4px
(шкала 4–8–12–16–24–32–48). Контрольные ширины: 360 / 768 / 1024 / 1280.
Каталог: 1 колонка до 768, фильтры шторкой; таблицы программ на мобильном —
горизонтальная прокрутка внутри контейнера, страница не скроллится вбок.

**Цвет.** Токены, не значения по месту: фон, поверхность, текст,
текст-приглушённый, акцент (действия и ссылки), акцент-конверсия (только
CTA целей — один на систему), успех/предупреждение/ошибка, границы.
Контраст: обычный текст ≥4.5:1, крупный и иконки ≥3:1 (WCAG AA);
проверка контраста пар токенов — автоматическая при сборке. Тёмная тема —
не в первом запуске (токены её допускают).

**Состояния** (обязательные для каждого компонента):
- Наведение и `focus-visible` (клавиатурный фокус всегда видим, свой стиль).
- Загрузка: скелетоны строк каталога и блоков карточки с
  зарезервированными размерами — нулевой сдвиг макета.
- Пустота: единый компонент «Информация отсутствует» (этапы 1–4) и
  «Ничего не нашли» с маршрутами выхода.
- Ошибки: полей форм (текст у поля, не только цвет), страница 404
  (поиск + популярные разделы + похожие адреса по слагу), страница 500
  (статическая, без зависимостей от базы и API).
- Выключенные значения фильтров (нулевой результат — этап 4).

**Компоненты** (реестр): строка каталога, карточка-факт, бейдж флага,
таблица программ, группа фильтра, слайдер стоимости с гистограммой,
хлебные крошки, пагинация, CTA-блок цели, вставка контента, аккордеон FAQ,
строка поиска с выдачей, панель сравнения, тост избранного.

**Доступность (WCAG AA).** Полная работа с клавиатуры (поиск — этап 3;
фильтры, аккордеоны, сравнение — стандартные aria-паттерны); цели касания
≥44×44px; `prefers-reduced-motion` уважается (анимации отключаемы);
семантические заголовки h1–h3 без пропусков уровней; alt у генерируемых
OG-изображений не требуется (они вне страниц), у иконок — aria-hidden +
текстовые подписи.

## 2. Производительность — бюджеты

| Метрика | Бюджет | Где меряется |
|---|---|---|
| LCP | ≤2,0 с | худшая эталонная страница, мобильный 4G |
| INP | ≤200 мс | острова фильтров и поиска |
| CLS | ≤0,1 | все эталонные |
| TTFB | ≤200 мс статика / ≤500 мс SSR-каталог | CDN / сервер |
| JS без островов | ≤30 КБ сжатого | каждая страница |
| Остров поиска / фильтров | ≤40 / ≤50 КБ | по острову |
| CSS | ≤50 КБ сжатого | глобально |
| Lighthouse | ≥95 | три эталона в CI каждого релиза |

Эталонные страницы CI: карточка вуза с 200+ программами (худший случай),
каталог с фильтрами, комбо-страница. Изображений в контенте почти нет
(фото в базе отсутствуют): OG-карточки генерируются при сборке, иконки —
один SVG-спрайт. Кэш: статика — immutable с хешем в имени; HTML — короткий
TTL с обновлением по импорту; API фасетов — до следующего снимка (этап 5).
Превышение бюджета = падение сборки, не предупреждение.

## 3. Аналитика

**Словарь событий** (без ПДн, без пользовательских идентификаторов;
модель этапа 4 — сервер не знает пользователя):
`search_query`, `search_click` (позиция, тип сущности), `filter_apply`
(поле, значение), `card_view` (тип карточки), `compare_add` / `compare_view`,
`favorite_add`, `quiz_start` / `quiz_step` / `quiz_branch` (знаю/не знаю) /
`quiz_complete`, `goal_click` (цель, зона, вариант — серверная регистрация,
этап 5), `outbound_site_click` (официальный сайт вуза), `article_read`
(прокрутка 70%).

**Контуры.** Яндекс Метрика — основной (рынок РФ; вебвизор и запись
сессий выключены — аудитория несовершеннолетняя); GA4 — контрольный;
серверный журнал `goal_click` — эталон конверсии (клиентские счётчики
режутся блокировщиками; расхождение клиент/сервер — само по себе метрика).

**Воронки и панель North Star.** Три воронки: органический вход → карточка →
квиз → цель; вход → поиск → карточка → цель; вход → каталог → сравнение →
цель. Панель: клики по целям из органики (сегмент по referrer),
органические сессии, проиндексированные страницы и CTR (API Вебмастера и
Search Console), доля нулевых выдач поиска, Core Web Vitals полевые.
Сквозной шов: UTM-шаблоны целей (этап 1) — владельцу рекомендовано
включить отметку источника на принимающей стороне; без неё платформа
честно отчитывается кликами, не покупками (ограничение Р2 зафиксировано).

**Эксперименты** — последовательные до достаточного трафика (этап 4),
события вариантов входят в `goal_click`.

## 4. DevOps и эксплуатация

- **Репозиторий:** monorepo — `pipeline/` (импорт), `site/` (страницы и
  острова), `api/`, `infra/` (compose, конфигурация). Схема БД — миграциями
  (единственный источник схемы).
- **CI на каждое изменение:** линт + типы + юнит-тесты + сборка + Lighthouse
  CI на эталонах + контракт импорта на фикстурах (включая повреждённый CSV
  этапа 0 как регресс). **CD:** статика → CDN; api + поиск + админка —
  Docker Compose на одном VPS. Старт сознательно одномашинный: чтение
  держит CDN; рост — вертикальный, затем вынос поиска и API отдельно;
  этого горизонта достаточно до десятков тысяч визитов в сутки.
- **Резервное копирование и восстановление.** PostgreSQL: ежедневный дамп,
  хранение 30 дней, недельная копия во втором хранилище; файлы снимков
  выгрузок — вечно (они маленькие). Ключевое свойство архитектуры:
  **база восстановима из снимков конвейером** — аварийный сценарий
  «пустой сервер → развернуть compose → прогнать последний снимок → сайт
  жив» репетируется раз в квартал и укладывается в час (RTO 1 час,
  RPO — последний дамп, сутки).
- **Мониторинг и оповещения:** внешняя проба доступности (сайт, поиск,
  API); сбор ошибок (класс Sentry); метрики: доля 5xx, время ответа API,
  **дней с последнего принятого импорта** (специфичная метрика платформы),
  всплеск 404, падение органических сессий >30% день к дню. Логи
  структурные, без ПДн, 30 дней.

## 5. Безопасность

- **Админка:** отдельный путь, вход только с двухфакторной аутентификацией
  (TOTP), RBAC этапа 5, каждое действие в `audit_log`, сессии короткие.
- **Веб-поверхность:** CSP (self + домены счётчиков, скрипты островов с
  nonce, inline запрещён); шаблонный эскейп повсюду (XSS); только
  параметризованные запросы (SQLi); CSRF-токены на всех изменяющих
  маршрутах админки и API; rate limit на поиск, API и `goal_click`
  (+ honeypot в квизе против ботов); HTTPS всюду, HSTS.
- **Секреты:** в переменных окружения/менеджере секретов, не в репозитории;
  ротация при смене исполнителей; аудит зависимостей в CI (блокирующий
  для критических уязвимостей).
- **ПДн:** архитектурно минимизированы (без аккаунтов, журналы без
  идентификаторов, вебвизор выключен) — поверхность 152-ФЗ близка к нулю;
  повторная оценка обязательна перед включением AI-помощника или кабинета.

## 6. Качество кода

- **Слои:** pipeline → ядро данных (витрины) → site/api; страницы не ходят
  в ядро напрямую мимо витрин; острова не знают о базе — только API.
- **Стандарты:** TypeScript strict во всех пакетах; линт и форматирование
  в CI (блокирующие); конвейер импорта — тоже TypeScript (единый стек);
  Python-скрипты `audit_*.py` остаются внешними контрольными инструментами
  (вторая, независимая проверка теми же цифрами — ценность, а не дубль).
- **Тесты:** юнит — нормализация городов, санитария цен, извлечение
  акронимов, генерация мета-слоя (полные/пустые данные); контракт импорта
  на фикстурах; снапшоты трёх эталонных страниц; e2e-смоук на выкладку:
  поиск → карточка → фильтр → квиз → `goal_click`; регрессионный набор
  поисковых запросов этапа 3 («мгу», «informatika», «byp», «информатике»).
- **Документация:** этапные документы `seo-platform/0*.md` играют роль
  журнала архитектурных решений; схема OpenAPI; runbook эксплуатации
  (импорт упал / поиск лежит / восстановление из снимка).

## 7. Итог этапа

1. **Решение.** Дизайн-система на токенах с WCAG AA и обязательными
   состояниями; производительность бюджетами с падением сборки; аналитика
   трёх контуров с серверным эталоном конверсии; одномашинный старт с
   CDN и восстановлением из снимков; безопасность с 2FA-админкой, CSP и
   минимизацией ПДн; monorepo с блокирующими проверками.
2. **Альтернативы.** Кластерная инфраструктура со старта — отклонена
   (стоимость без нагрузки); запись сессий (вебвизор) — отклонена
   (несовершеннолетние); клиентская-только аналитика конверсии — отклонена
   (блокировщики); конвейер на Python — отклонён в пользу единого стека,
   Python сохранён как независимый контролёр.
3. **Причины выбора.** Малая команда → минимум движущихся частей;
   аудитория → минимум данных о ней; SEO-цель → бюджеты скорости жёсткие,
   в CI, не в пожеланиях.
4. **Риски.** Одна машина — единая точка отказа (смягчение: CDN отдаёт
   статику при лежащем сервере, репетируемое восстановление за час);
   блокировщики искажают клиентскую аналитику (серверный эталон);
   бюджеты производительности могут конфликтовать с будущими скриптами
   маркетинга — конфликт решается в пользу бюджета.
5. **Ограничения.** Никакой записи ПДн; никакого inline-JS вне nonce;
   ручные операции с базой запрещены (только конвейер и админка).
6. **Критерии качества.** CI зелёный = все бюджеты соблюдены; квартальная
   репетиция восстановления пройдена; регрессионный набор поиска зелёный;
   контраст токенов проходит автоматическую проверку.
7. **Checklist готовности.** [x] Дизайн-система с измеримыми параметрами.
   [x] Бюджеты производительности в CI. [x] Словарь событий и воронки.
   [x] Схема выкладки, копий, мониторинга, восстановления. [x] Модель
   безопасности. [x] Стандарты и тесты. [ ] Подтверждение владельца →
   этап 7 (дорожная карта).

**Этап 7 (после подтверждения):** дорожная карта — разбивка на независимые
этапы с целями, результатами, рисками, критериями готовности и оценкой
сложности; порядок запуска от минимального индексируемого ядра до полного
инвентаря; что требует твоих решений по ходу (C8, домен, точка конверсии
первой кампании).
