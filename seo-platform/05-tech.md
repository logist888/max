# SEO-платформа — Этап 5: технологии, база данных, API, админка

> Дата: 11.07.2026. Этапы 0–4 подтверждены; решение владельца от 11.07.2026:
> AI-помощник вынесен за пределы первичного запуска (слот сохранён).
> **Допущение этапа (C8 не отвечен):** на сборку и сопровождение доступен
> один веб-разработчик (TypeScript) помимо Rust-команды основной платформы.
> Если сопровождать сможет только Rust-команда — включается путь Б
> (раздел 1); пересмотреть до начала разработки.

## 1. Стек рендеринга

Профиль нагрузки (из этапов 1–2): ~9,6 тыс. канонических страниц; данные
меняются пакетно (импорт раз в дни/недели); интерактивность сосредоточена
в четырёх островах (поиск, фильтры, сравнение, квиз); требование —
Lighthouse ≥95 и минимальный JS.

**В1. Next.js (React, ISR).** Плюсы: индустриальный стандарт, наём прост,
ISR обновляет страницы без пересборки. Минусы: React-гидратация тянет
базовый JS-бюджет даже на статических страницах; ISR-сложность не нужна
при пакетных данных; сервер Node в проде обязателен.

**В2. Astro (генерация + острова) + лёгкий API-сервис.** Плюсы: страницы
по умолчанию без клиентского JS — бюджет тратится только на четыре
острова; полная регенерация 10 тыс. страниц — минуты, совпадает с тактом
импорта; SSR-режим для параметрических страниц каталога есть; фреймворк
островов любой. Минусы: наём уже, чем React (смягчение: острова можно
писать на React внутри Astro); меньше готовых корпоративных практик.

**В3. Rust — Axum + шаблоны + HTMX (путь Б).** Плюсы: единый язык с
основной платформой MainExperts — сопровождает существующая команда;
лучший TTFB; один бинарь в проде. Минусы: скорость продуктовой итерации
интерфейса (фильтры уровня Booking, квиз) заметно ниже; экосистема
интерфейсных компонентов беднее; SEO-инструментарий (OG-карточки,
sitemap-генераторы) пишется руками.

**Выбор: В2 (Astro), при условии допущения о TypeScript-разработчике.**
Причины: JS-бюджет — прямое требование производительности; такт «импорт →
пересборка» естественно ложится на генерацию; острова изолируют сложность.
В1 отклонён как плата за ненужную динамику, В3 остаётся официальным путём
отхода: модель «витрины → страницы» одинакова для обоих путей, смена пути
не трогает этапы 1–4. Решение ратифицируется ответом C8.

Схема выкладки: статика на CDN/edge; параметрические страницы каталога и
API — маленький серверный процесс; пересборка страниц — шаг конвейера
импорта (меняются только затронутые страницы: генератор сравнивает витрины
по хешу).

## 2. База данных

PostgreSQL (истина + витрины; выбор СУБД безальтернативен по факту:
реляционное ядро с JSONB-полями, материализованные витрины, один сервер).

Ядро (ER словами; ключи и индексы — в скобках):

- `source_snapshot` — снимок выгрузки (sha256 unique, дата, статус
  принят/отклонён, отчёт контракта jsonb).
- `region` (slug unique), `city` (slug unique, region_id FK+idx,
  raw_names[] — все сырые написания источника).
- `organization` — текущее состояние (id источника PK, slug unique,
  вид: головной/филиал/зарубежный, parent_id FK nullable, city_id FK+idx,
  три имени, адрес, контакты, флаги, места в общежитии nullable,
  useful_links jsonb, socials jsonb, first_seen/last_seen snapshot FK) —
  исчезновение из снимка не удаляет строку (жизненный цикл этапа 2).
- `organization_version` — журнал: (org_id, snapshot_id) PK, payload jsonb;
  точечная история изменений и сырьё для страниц «что изменилось».
- `ugs_group` (code PK, name, реквизиты нормативного источника),
  `direction` (okso PK, name, ugs_code FK, level_code FK),
  `level` (code PK, система: действующая/пилот/не-выгружается),
  `admission_campaign` (year unique).
- `program_offer` (id, org_id FK+idx, okso FK, form, place_type,
  places, cost nullable — санитария цен на импорте, campaign_id FK,
  snapshot_id FK; составной idx (okso, campaign_id) для комбо-витрин,
  (org_id, campaign_id) для карточек).
- Управляющие: `conversion_goal`, `cta_placement` (этап 1),
  `curated_landing` (slug unique, filter_def jsonb, intro, active),
  `alias` (entity_type+entity_id idx, source: база/авто/куратор),
  `redirect` (from_path unique, to_path, код 301/410),
  `article` (slug unique, статус черновик/опубликована, автор, даты),
  `audit_log` (кто, что, до/после jsonb, когда; только запись).

Витрины (материализуются шагом импорта, читаются сайтом и поиском):
`mv_card_org` (карточка вуза одной строкой), `mv_catalog_row`,
`mv_geo_agg` (город/регион), `mv_direction_agg`, `mv_combo` (только
комбинации выше порогов этапа 2), `search_export` (документы для движка).
Пересборка витрин полная (секунды на этом объёме), атомарная подмена
через переименование.

Конвейер импорта (сводит правила этапов 0–4):
1. Загрузка файла в админке → контракт `audit_json.py` (валидность,
   объёмы ±10% от прошлого снимка — предупреждение куратору).
2. Стейджинг → нормализация городов → санитария цен (<20 тыс. → пусто +
   журнал) → извлечение акронимов в алиасы.
3. Отчёт различий: новые/исчезнувшие вузы, изменения цен и мест —
   куратор смотрит и принимает снимок.
4. Применение: обновление ядра, версии, витрины, поисковый индекс,
   sitemap, регенерация изменённых страниц. Один снимок — одна транзакция
   принятия; откат = возврат указателя текущего снимка.

## 3. API

Потребители: собственный фронт (острова) и генератор страниц. Внешних
потребителей нет, вложенных запросов произвольной формы нет.

- REST против GraphQL против гибрида: GraphQL оправдан разнообразием
  клиентов и форм запросов — здесь их нет; гибрид удваивает поверхность.
  **Выбор: REST (JSON), /api/v1, максимум десяток маршрутов:** подсказки
  поиска, полная выдача, фасетные счётчики, строки каталога по фильтру,
  данные сравнения, маршрутизация результата квиза, регистрация клика по
  цели, состояние здоровья. Генератор страниц читает витрины напрямую из
  базы, минуя HTTP.
- Контракты фиксируются схемами (OpenAPI), ответы кэшируются заголовками
  (фасетные счётчики — до следующего импорта: у данных нет других причин
  меняться).
- Клик по цели: серверная регистрация (тип страницы, зона, цель, вариант,
  без идентификаторов личности) → это событие конверсии платформы
  (этап 1, Р2).

## 4. Административная панель

Сравнение: (а) полностью своя админка; (б) готовая headless-CMS для всего;
(в) инструмент класса Directus поверх схемы PostgreSQL (авто-CRUD, RBAC,
журнал) + 2–3 кастомных экрана.

Своя — дорого по времени при малой команде; чистая headless-CMS не знает
наших сущностей данных (вузы, снимки) и превращается в параллельную базу.
**Выбор: (в).** Авто-CRUD закрывает справочники и управляющие таблицы
(цели, размещения, алиасы, редиректы, статьи с черновиками и публикацией),
штатный RBAC и журнал действий совпадают с требованиями задания. Кастомные
экраны: «Импорт снимка» (загрузка, отчёт контракта, различия, принятие),
«Курация связей» (филиал → головной, слияния с 301), «Кураторские
посадочные» (сохранённый фильтр → адрес + вводный текст). Риск: зависимость
от инструмента — смягчается тем, что вся истина в PostgreSQL и админка
заменяема без миграции данных.

Роли (минимум, расширяемо): владелец (всё), куратор данных (импорт, связи,
алиасы, редиректы), редактор (статьи, вводные тексты, FAQ-правки), аналитик
(чтение + выгрузки). Каждое изменение — в `audit_log`; массовые операции —
только через конвейер импорта, не руками в таблицах.

## 5. Итог этапа

1. **Решение.** Astro-генерация с островами + PostgreSQL (ядро + витрины) +
   Meilisearch + REST /api/v1 + Directus-класс админка с тремя кастомными
   экранами; конвейер импорта с контрактом, санитарией, отчётом различий и
   атомарным принятием.
2. **Альтернативы.** Рендеринг: Next.js / Astro / Rust+HTMX (раздел 1);
   API: REST / GraphQL / гибрид; админка: своя / headless-CMS / поверх
   схемы. Все сравнения — в тексте этапа.
3. **Причины выбора.** JS-бюджет и такт пакетного импорта; отсутствие
   внешних потребителей API; малая команда — минимум самописного там, где
   есть штатное, и полный контроль там, где живёт истина (ядро БД,
   конвейер).
4. **Риски.** Главный — допущение о TypeScript-разработчике (C8): путь Б
   (Rust+HTMX) сохранён и не ломает этапы 1–4; зависимость от админ-
   инструмента (истина в PostgreSQL, инструмент заменяем); Meilisearch —
   путь отхода к PostgreSQL зафиксирован этапом 3.
5. **Ограничения.** Никакой записи ПДн пользователей в базу (этап 4);
   ручные правки данных вне конвейера запрещены; счётчик источника не
   публикуется (Д4 открыт).
6. **Критерии качества.** Полный цикл «снимок → сайт» проходит одним
   конвейером за ≤30 минут с ручным шагом только на принятии; страницы
   карточек не тянут клиентский JS вне островов; каждый API-маршрут
   описан схемой; каждое действие в админке оставляет след в журнале.
7. **Checklist готовности.** [x] Три варианта по каждому решению.
   [x] ER-ядро, витрины, индексы, конвейер. [x] REST-поверхность.
   [x] Админка, роли, кастомные экраны. [ ] Ратификация допущения C8
   владельцем. [ ] Подтверждение → этап 6.

**Этап 6 (после подтверждения):** эксплуатация и качество — аналитика
(события, воронки, сквозная связка UTM), производительность (бюджеты
Core Web Vitals, размеры), DevOps (CI/CD, контейнеры, резервные копии,
мониторинг), безопасность (доступы, защита админки, журналы), стандарты
кода и тестирование. Затем этап 7 — дорожная карта запуска.
