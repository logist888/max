# 08. Roadmap создания документов

> Раздел 12 модуля DMS. Снимок 12.07.2026. Авторская разработка (Claude Code). Роадмап
> определяет **порядок создания** документов по четырём этапам зрелости. Порядок = топологическая
> сортировка дерева зависимостей (`07-trees.md`) с приоритетом Must×Critical (`03-classification.md`,
> 4.6). Опора: принцип канона «стандарт без масштаба не работает» и V4.1 «наблюдаемость →
> прогноз → рекомендации → оптимизация». Утверждает основатель.

Принцип роадмапа: **документ вводится, когда цена его отсутствия превышает цену ведения** —
не раньше (иначе бюрократия душит стадию), не позже (иначе риск реализуется). Четыре этапа
соответствуют уровням зрелости 4.5 и стадийной модели S0–S2 канона (`../boards/04-stage0-mvp.md`).

---

## Этап 1 — Запуск (MVP · до и вокруг первого вебинара)

**Стадия компании:** подготовка вебинара (предв. 4 июля 2026, перенос), выручка через Поток-1,
команда ≤ 8, повторяемой выручки P2 нет. **Правило отбора:** только то, без чего запуск
**незаконен, недостоверен или неатрибутируем**. Всё Must×Critical + жёсткие блокеры.

| Документ | Почему на Этапе 1 |
|---|---|
| D1-POL-03 Данные несовершеннолетних | Регуляторный стоп-фактор: без него платный трафик на детскую аудиторию незаконен |
| D1-POL-02 Privacy · D1-POL-07 Согласия · D1-RGS-05 Согласия · D1-CHK-02 Gate | Комплаенс-контур, разрешающий запуск трафика (жёсткая зависимость) |
| D1-CTR-03 ToS · D1-CTR-04 Оферта · D1-CTR-01 Трудовой шаблон · D7-CTR-01 Юрлицо | Правовое оформление отношений и приёма денег |
| D5-SPC-01 Методология скрининга | Блокер №1: без неё квиз/отчёт/воронка без основания |
| D5-GDL-01 Дисклеймер психодиагностики | Держит продукт в границах психодиагностики |
| D4-SPC-01/02/03 Профиль/Квиз/Отчёт · D4-SPC-04 PRD подписки | Ядро продукта; без спецификаций качество невоспроизводимо |
| D2-RGM-02 Воронка P2 · D2-SOP-02 Тексты · D2-FRM-01 Захват e-mail · D2-POL-01 Цена P2 | Управляемый прогон гипотезы скрининга |
| D2-RMP-01 Маркетинг-стратегия · D2-CLF-01/02/03 · D2-STD-01 UTM · D2-TPL-01 ТЗ | Атрибутируемый трафик; ДРР-контроль |
| D3-RGM-01 Биллинг · D3-PRC-01 Сведение оплат · D3-SPC-01 Юнит-экономика · D3-RGS-02 Runway · D3-CTR-01 Провайдеры | Приём денег, атрибуция, правда о прибыльности по потокам |
| D4-DAT-02 Словарь метрик · D4-AIA-01/02 Промпты | Исполнимость метрик; воспроизводимость AI-отчёта |
| D7-POL-01 Миссия/ценности · D7-RMP-01 Стратегия · D7-RGS-01 OKR · D7-DSH-01 Owner-борд | Ось решений и фокус (S1-борд «трафик→оплаты») |
| D5-RGS-01 Мастер-реестр · D5-TPL-01 Мета-шаблон | Сама система документации управляема с первого дня |
| D6-POL-02 Источники данных · D6-GDL-01 Обезличивание | Достоверность и юр-безопасность каталогов/отчётов |
| D1-ARC-01 Оргструктура · D1-TPL-01 Профиль роли · D1-RGS-06 Реестр рисков | Минимум орг- и риск-контура |

**Причина этапа:** это набор, снимающий три зашитых противоречия цели $1M (`../01-strategy.md`):
законность (комплаенс), достоверность (методология), измеримость по потокам (юнит-экономика +
словарь метрик). Всё остальное ждёт данных.

## Этап 2 — Рост (Growth · повторяемая выручка P2, первые наймы)

**Стадия:** воронка даёт повторяемые оплаты (триггер S1→S2 канона: 4 недели данных + первое
решение по данным), первые наймы, ≥ 2 команд. **Правило отбора:** документы, которых требует
**передача знания** (наём) и **масштабирование каналов/данных**.

| Группа | Документы | Почему на Этапе 2 |
|---|---|---|
| Найм/адаптация | D1-RGM-01, D1-CHK-01, D1-PLN-01, D1-RGS-01, D1-RGM-02 | Наём требует воспроизводимого онбординга и ритмов |
| Процессы D2 | D2-RGM-01 Трафик, D2-SOP-01, D2-RGM-03 Продажи, D2-RGS-01/02, D2-DSH-01/02, D2-GDL-01/02/03 | Каналы масштабируются — нужен регламент и бренд-рамка |
| Данные | D4-DAT-01 Data Dictionary, D4-DAT-03 Глоссарий, D4-CLF-01, D4-STD-06/07, D4-SPC-05 события | Появились данные — нужен единый источник истины |
| AI-контур | D1-POL-09 AI Policy, D4-AIA-03/04, D5-STD-03 eval, D5-SOP-01 review, D4-STD-08 версии промптов | AI в проде — нужна управляемость и оценка |
| Продукт/инж | D4-STD-01 freemium, D4-RMP-01/02, D4-RGS-01 бэклог, D4-ARC-01, D4-STD-03/04, D4-SOP-01, D4-DSH-01, D4-GDL-01 | Продукт растёт — нужны стандарты разработки |
| Качество/СМК | D5-POL-01/02, D5-STD-02, D5-CHK-01, D5-PRC-04/05, D5-STD-05, D5-KB-01 | Качество нельзя держать «в голове» на 2+ командах |
| Экспертная сеть | D6-RGM-01, D6-STD-01, D6-CHK-01, D6-CTR-01, D6-POL-01, D6-RGS-01, D6-DSH-01, D6-KB-01 | Онбординг экспертов масштабируется |
| Каталоги | D6-CAT-01, D6-CAT-02, D6-CLF-01 | Снятие блокера №2 (парсер) открывает каталоги |
| Финансы | D3-POL-01/02/03, D3-RPT-01, D3-DSH-01, D3-CHK-01 | Учётная дисциплина, международные платежи (Stripe) |
| Governance | D1-POL-01 Этика, D1-POL-04/05/06, D1-STD-01, D1-FRM-01, D1-RGS-04, D7-POL-02/03, D7-ARC-01 | Оргзрелость требует политик и защиты данных |

**Причина этапа:** переход от «работает у основателя» к «работает у команды». Документ здесь —
инструмент передачи и масштабирования, а не контроля ради контроля.

## Этап 3 — Масштабирование (Scale · кратный рост, несколько рынков)

**Стадия:** кратный рост нагрузки и штата, СНГ + MENA, несколько продуктов. **Правило отбора:**
документы, которых требует **координация между функциями** и **надёжность под нагрузкой**.

| Группа | Документы | Почему на Этапе 3 |
|---|---|---|
| Инциденты/надёжность | D4-PRC-01 SRE, D4-STD-05 наблюдаемость, D1-PRC-01 инциденты ИБ, D1-RGS-07 | Нагрузка ⇒ отказы дорого стоят |
| Данные/BI | D4-DAT-04 master-data, D4-DAT-05 lineage, D4-RGS-03 витрины | Много источников ⇒ нужен lineage и master-data |
| Комплаенс масштаба | D1-PRC-02 DSAR, D1-RGS-04 RoPA, D1-POL-10 AI Security, D7-POL-04 ERM, D7-RGS-02 | Больше субъектов/рынков ⇒ больше обязательств |
| СМК | D5-PRC-01/02 несоответствия/КД-ПД, D5-STD-04 enablement | Качество на масштабе через процессы, не героизм |
| Финансы/HR | D3-PRC-02 закрытие периода, D1-POL-08 вознаграждение, D1-RGS-02 компетенции, D1-RPT-01 | Регулярность учёта и HR-аналитика |
| Продукт | D4-STD-02 локализация (MENA/AR), D4-RGS-02 техдолг, D2-KB-01, D2-SPC-01 CRM | Мультирынок и управление долгом |
| Экспертная сеть | D6-RGM-02 поддержка, D6-RPT-01, D6-CAT-03 работодатели, D6-CTR-02 партнёрства | Экосистема расширяется |

**Причина этапа:** на масштабе ломается то, что держалось на устной координации; документ
становится «единым источником истины» между функциями (принцип Single Source of Truth канона).

## Этап 4 — Enterprise (зрелая оргструктура, аудит, инвесторы)

**Стадия:** внешний аудит/комплаенс, сертификация, due diligence, партнёрства/инвесторы.
**Правило отбора:** документы, которых требует **внешняя проверяемость** и **сертифицируемость**.

| Группа | Документы | Почему на Этапе 4 |
|---|---|---|
| Аудит/СМК | D5-PRC-03 внутренний аудит; полный набор ISO 9001-совместимых процедур | Сертификация/аудит требуют аудируемости |
| Governance | Полный набор COBIT/ITIL-совместимых политик; D7-POL-02 расширенное корп-управление | Due diligence, совет директоров |
| Отчётность | Инвесторская и регуляторная отчётность (расширение D3-RPT-01, D7-RPT-01) | Внешние стейкхолдеры |

**Причина этапа:** документы перестают быть внутренним инструментом и становятся объектом
внешней проверки. Раньше этой стадии их полнота — избыточность (та же ловушка «стандарт без
масштаба»).

## Сводный порядок и правило перехода между этапами

```
Этап 1 (MVP)      ~34 Must-документа: законность + достоверность + измеримость
   ↓ триггер: повторяемая выручка P2 (4 нед данных + решение по данным)
Этап 2 (Growth)   ~45 документов: передача знания + масштаб каналов/данных
   ↓ триггер: кратный рост штата/нагрузки, второй рынок
Этап 3 (Scale)    ~30 документов: координация функций + надёжность
   ↓ триггер: внешний аудит / инвестор / сертификация
Этап 4 (Enterprise) остаток: внешняя проверяемость
```

> Инвариант перехода (перенос S1→S2 канона): этап считается пройденным **не по календарю, а по
> факту** — когда сработал триггер следующего. Форсировать этап документами раньше триггера —
> против принципа V4.1 (аналитика/контроль до наблюдаемости усиливают шум).

> Роль критика: соблазн на стадии запуска — построить сразу Enterprise-набор политик (как MMS
> описывает enterprise-борды раньше данных, `../08-board-system.md`, критический разбор). Роадмап
> сознательно откладывает большинство политик на Growth/Scale, оставляя на MVP только
> блокеры-и-законность. Полнота реестра — это карта, а не бэклог на завтра.
