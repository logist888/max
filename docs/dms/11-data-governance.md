# 11. Data Governance

> Раздел 15 модуля DMS. Снимок 12.07.2026. Авторская разработка (Claude Code). Раздел определяет
> управление данными как классом управляемых документов. Опора: DAMA-DMBOK (Data Management
> Body of Knowledge), DCAM. **Важно:** реляционная модель и словарь метрик уже частично
> существуют в каноне (`../10-data-model.md`, таблица `kpi_definitions`) — этот раздел не дублирует
> их, а надстраивает **governance-слой** (владение, роли, качество, происхождение), которого в
> каноне нет. Утверждает основатель.

Данные MainExperts — ядро продукта (профиль, метрики, каталоги) и источник регуляторного риска
(детские/психоданные). Управление данными без владельцев и стандартов качества ведёт к
расхождению цифр (борды неисполнимы) и к нарушению защиты данных.

## 15.2. Роли данных (Data Ownership) — чего в каноне нет

| Роль | Ответственность | Кто (цель / старт) |
|---|---|---|
| **Data Owner** | Отвечает за домен данных (смысл, доступ, риск) на уровне функции | владелец домена: CFO (финданные), CMO (маркетинг), Head of Expert Net (эксперты), Product Owner (профиль) |
| **Data Steward** | Ведёт словари, качество, именование, справочники | D4 (Data/Analyst); старт — Александр/аналитик |
| **Data Custodian** | Техническое хранение и доступ (БД, бэкапы) | CTO/DevOps |
| **DPO** | Защита ПДн, согласия, детские/психоданные | D1 (Compliance) |

> Инвариант (перенос из бордов): **у каждого объекта данных ровно один Data Owner** — как у KPI
> запрещён показатель без ответственного (`../boards/02-roles-access.md`). Data Steward может
> быть один на несколько доменов на старте, но владелец домена — всегда именованный.

## 15.3. Каждый элемент — назначение и правило

- **Data Governance Policy.** Рамка: кто владеет данными, как классифицируются, кто имеет доступ,
  как обеспечивается качество и защита. Связана с `D1-POL-04` (хранение), `D1-POL-05` (ИБ),
  `D1-POL-03` (детские данные).
- **Data Dictionary (D4-DAT-01).** Каталог сущностей, таблиц, полей с типами и смыслом. Надстройка
  над схемой `../10-data-model.md`: добавить владельца поля, гриф конфиденциальности, PII-метку.
- **Metric Dictionary (D4-DAT-02).** Словарь метрик поверх `kpi_definitions`. **Главная задача:**
  унифицировать префикс `KPI-` (борды) vs `KPI_` (модель) — расхождение канона; закрепить один
  стиль решением основателя. Один расчёт на показатель (Single Source of Truth).
- **Business Glossary (D4-DAT-03).** Бизнес-термины на человеческом языке (что такое «лид»,
  «зона риска», «Профиль 360»), единый словарь для всех документов. Ссылка из мета-шаблона
  (раздел «Термины»).
- **Master Data (D4-DAT-04).** Справочные наборы-эталоны (рынки, каналы, тарифы, статусы) —
  единая версия истины для справочников.
- **Data Lineage (D4-DAT-05).** Происхождение: от события (`EVT_/ORDER_`) через витрину (`v_*`)
  до метрики на борде. Нужен для доверия к цифрам и разбора расхождений.
- **Data Quality (D4-STD-06).** Измеримые требования к данным: полнота, точность, актуальность,
  непротиворечивость; правила валидации (например, UTM против закрытого словаря `MK_`).
- **Классификаторы ядра (D4-CLF-01).** Нормативные закрытые словари `LST_/EVT_/ORDER_/MK_/PG_/
  CELL_/REF_` — единая кодировка (`../12-traffic-platform-decisions.md`).
- **Стандарт именования (D4-STD-07).** `snake_case` таблицы мн.ч., `<Entity>_ID` ключи, `ПРЕФИКС_КОД`
  значения — из `../10-data-model.md`, зафиксировать как стандарт.

## 15.4. Классификация данных и защита (стык с комплаенсом)

| Класс данных | Примеры | Режим |
|---|---|---|
| Публичные | каталоги профессий/вузов (архетипы) | открыто; правило источник+дата |
| Внутренние | метрики, кампании, финсводки | по ролям (RBAC) |
| Персональные (ПДн) | e-mail, профиль пользователя | согласие, retention, DSAR |
| **Особая категория** | **данные несовершеннолетних, психомодуль** | **родительское согласие, повышенная защита, дисклеймер, ограниченный доступ, особый срок хранения** |

> Особая категория — прямой стык с `../05-risk-compliance.md` и `D1-POL-03`. Data Governance
> и Compliance здесь пересекаются: Data Owner отвечает за смысл и доступ, DPO — за законность.
> Психомодуль полностью приватен (виден только владельцу и допущенным) — реализуется правами
> доступа на уровне объекта.

## 15.5. Жизненный цикл данных

```
Событие (append-only) → Валидация качества (D4-STD-06) → Сущность/Факт (модель) →
Витрина (v_*) → Метрика (kpi_definitions) → Борд/Отчёт → Решение
     ↑ Lineage прослеживает весь путь назад (D4-DAT-05)
     ↑ Retention/удаление по D1-POL-04 (особая категория — особый срок)
```

## 15.6. Уровни зрелости Data Governance

| Зрелость | Что вводится |
|---|---|
| MVP | D4-DAT-02 (словарь метрик, унификация KPI-/KPI_), классификация данных, режим детских данных |
| Growth | D4-DAT-01 (Data Dictionary + владельцы/PII), D4-DAT-03 (глоссарий), D4-STD-06/07, назначение Data Steward |
| Scale | D4-DAT-04 (master-data), D4-DAT-05 (lineage), автоматизированный Data Quality, RoPA |
| Enterprise | DAMA-совместимый контур, каталог данных, внешний data-аудит |

---

## 15.7. Незакрытое расхождение (реестр фиксирует)

**Префикс KPI:** `KPI-` (борды/стадии, дефис) vs `KPI_` (реляционная модель, подчёркивание).
Место разрешения — **D4-DAT-02 (Словарь метрик)**, решение основателя. До унификации борды и
модель данных ссылаются на «одну и ту же» метрику разными кодами — источник расхождения цифр.
