# 02. Карта процессов

> Раздел 3 модуля DMS. Снимок 12.07.2026. Авторская разработка (Claude Code). Опора: BPM CBOK
> (иерархия процесс→подпроцесс→операция), ISO 9001 (процессный подход), APQC PCF (референс
> классификации процессов). Согласовано с BPMN-модулем канона (`../bpmn/`, если ведётся)
> и бордами MMS. Утверждает основатель.

Карта строится в три уровня: **сквозной процесс (value stream) → подпроцесс → операция**.
Двенадцать процессов P01–P12 введены в `00-architecture.md`. Ниже — для каждого: ведущий
Division, подпроцессы, входы/выходы, обслуживающие документы (по ID из `04-registry.md`).

Процессы делятся на три группы (APQC-подход):
- **Управляющие** (governing): P01, P12 — задают рамку.
- **Основные** (core / создающие ценность): P02–P08 — поток от спроса до выдачи и сети.
- **Обеспечивающие** (enabling): P09, P10, P11 — люди, данные, AI.

---

## Легенда связи «процесс ↔ документ»

Каждый процесс связан с документами тремя типами связи (по требованию раздела
«Бизнес-процессы»):
- **Обслуживает** (S, serves) — документ управляет ходом процесса.
- **Инициирует** (I, initiates) — процесс порождает документ/запись.
- **Завершается** (C, closes) — использование документа завершает процесс.

## Управляющие процессы

### P01 — Стратегическое планирование и OKR-цикл · D7

- **Подпроцессы:** актуализация миссии/стратегии → постановка годовых целей → декомпозиция в
  OKR по Division → квартальный ретро и пересмотр → распределение капитала.
- **Вход:** рыночные данные, свод Owner Dashboard, ограничения runway. **Выход:** OKR-набор,
  утверждённая стратегия, бюджет.
- **Роли:** Owner (A), C-level (R), Analyst (C).
- **Документы:** S — Стратегия, Политика целеполагания; I — OKR-реестр, Дорожная карта
  компании; C — Протокол стратегической сессии.

### P12 — Комплаенс, риски, защита данных · D1 (+D5)

- **Подпроцессы:** идентификация риска → оценка → выбор реакции → внедрение контроля →
  мониторинг → инцидент-менеджмент; ведение согласий; DPIA для детских/психоданных.
- **Вход:** регуляторные требования, карта данных, инциденты. **Выход:** контроли, согласия,
  реестр рисков в актуальном состоянии.
- **Роли:** DPO/Compliance (A), Legal (C), CTO/Data (C), Quality (R).
- **Документы:** S — Политика защиты данных несовершеннолетних, Политика хранения/удаления,
  Политика ИБ; I — Реестр рисков, Реестр согласий, DPIA-форма; C — Акт оценки соответствия.
- **Инвариант:** узел компаянса обязателен для любого процесса, касающегося детских данных или
  психомодулей (`../05-risk-compliance.md`).

## Основные процессы

### P02 — Генерация спроса и трафик · D2

- **Подпроцессы:** планирование кампании → сборка измерительной ячейки (`CELL_`) → запуск на
  источник (`MK_`) → сбор событий → атрибуция → оптимизация по ДРР/CPL → решение
  «масштабировать/закрыть пару».
- **Вход:** оффер, бюджет ≥$400, посадочная (`PG_/LST_`). **Выход:** лиды, оплаты P2, статус
  пары (основная/тестовая/закрытая).
- **Роли:** CMO (A), Traffic-специалист (R), Analyst (C), Payments Owner (C, атрибуция).
- **Документы:** S — Регламент трафика, Классификатор `MK_/PG_/CELL_`, Стандарт UTM-разметки;
  I — ТЗ подрядчику (форма 11 пунктов), Отчёт по кампании; C — Решение по паре источник-посадочная.

### P03 — Скрининг → freemium → апсейл (воронка P2) · D2→D4

- **Подпроцессы:** выбор роли → квиз (≈18 вопросов, 6 шкал) → мини-отчёт «N зон риска из 6» →
  захват e-mail → 3 CTA → регистрация → Профиль 10 (freemium) → апсейл Профиль 360 → оплата →
  автогенерация отчёта → выдача.
- **Вход:** трафик, спецификация квиза, методология скрининга. **Выход:** зарегистрированный
  пользователь, freemium-профиль, оплаты, AI-отчёт.
- **Роли:** CMO/Growth (A воронка), Product Owner (A продукт/цена), Backend (R), Methodologist
  (C методология), Compliance (C детские данные).
- **Документы:** S — Регламент воронки P2, Спецификация квиза, SOP «Правила вывода текстов
  мини-отчёта», Стандарт freemium-логики, Политика данных несовершеннолетних; I — событие
  `EVT_SCREENING_DONE`, запись профиля; C — выданный отчёт (по Спецификации отчёта).
- **Инвариант:** гипотеза скрининга — ставка, не факт; выводы маркируются как рисковые.

### P04 — Премиальная продажа (P1, high-touch) · D2/D7

- **Подпроцессы:** контакт по рекомендации → квалификация → диагностика потребности →
  предложение (лесенка 50К→10 млн / £-пакеты) → согласование → оплата → сопровождение.
- **Вход:** нетворк основателя, реферал. **Выход:** премиум-продажа, клиент «Год рядом»/Family
  Office.
- **Роли:** Owner (A, R — личный канал), Commercial Director (C).
- **Документы:** S — Плейбук премиум-продажи (конфиденциально, поток-1), Прайс-лист P1; I —
  Договор оказания услуг P1, карточка HNW-клиента; C — акт/закрытие сделки.
- **Инвариант:** метрики P1 не смешиваются с P2; детали в `../private/stream-1-hnw.md`
  (вне общего git).

### P05 — Производство цифрового профиля и AI-отчёта · D4

- **Подпроцессы:** сбор данных модулей → расчёт весов/индексов → генерация AI-отчёта (≈40 стр.)
  → self-review/eval → выдача → пересчёт при обновлении (пересдача раз в 6 мес).
- **Вход:** ответы теста, загруженные данные, промпты, RAG-корпус. **Выход:** цифровой профиль,
  AI-отчёт.
- **Роли:** Product Owner (A), AI Engineer (R), Quality/eval (C), Methodologist (C).
- **Документы:** S — Спецификация цифрового профиля, Спецификация AI-отчёта, Библиотека
  промптов, Стандарт качества отчёта, eval-правила; I — версия профиля, лог генерации; C —
  утверждённый отчёт.
- **Инвариант:** переменная стоимость единицы ≈ 0 (автоматизировано); AI не заменяет решение.

### P06 — Управление подпиской и биллинг · D3→D4

- **Подпроцессы:** выбор тарифа (Free/Pro/Ultima) → оплата (Робокасса→Stripe) → активация →
  продление/отмена → сведение оплаты с источником трафика (вручную, cross-domain).
- **Вход:** тариф, платёжные данные. **Выход:** активная подписка, транзакция, атрибуция.
- **Роли:** CFO (A), Payments Owner/Даниил (R), Backend (R активация).
- **Документы:** S — Регламент биллинга и подписки, Оферта подписки, Политика возвратов; I —
  `ORDER_RENEW`, счёт/чек; C — активированная/закрытая подписка.

### P07 — Онбординг и управление сетью экспертов · D6

- **Подпроцессы:** заявка эксперта → авто-анализ сертификатов (AI, OpenRouter) → ручное
  подтверждение → профиль эксперта → подписка эксперта (3 мес бесплатно) → мониторинг качества
  (rating, NPS) → развитие/коррекция.
- **Вход:** заявка, сертификаты. **Выход:** активный эксперт в сети, профиль эксперта.
- **Роли:** Head of Expert Network (A), Support (R онбординг), Quality Manager (C).
- **Документы:** S — Регламент онбординга эксперта, Стандарт качества эксперта, Чек-лист
  верификации сертификатов, Оферта эксперта; I — карточка эксперта, запись рейтинга; C —
  активный статус эксперта.

### P08 — Ведение каталогов (профессии/вузы/работодатели) · D6→D4

- **Подпроцессы:** сбор из источников (O*NET/ESCO/hh.ru) → кроссвалидация (ISCO-SOC) →
  обезличивание/архетипизация → публикация в каталог → обновление и версия.
- **Вход:** внешние базы, парсер рынка труда (**блокер №2**). **Выход:** каталоги на платформе.
- **Роли:** Content-куратор (R), Data Engineer (R), Methodologist (C), Legal (C по IP/согласиям).
- **Документы:** S — Стандарт ведения каталога, Классификатор профессий (RIASEC/Job Zones),
  Политика источников данных (источник+дата), Гайдлайн обезличивания; I — записи каталога; C —
  опубликованная версия каталога.
- **Инвариант:** каждый факт-премиум несёт источник+дату+ссылку; профили реальных людей без
  согласия запрещены — только архетипы.

## Обеспечивающие процессы

### P09 — Найм и адаптация сотрудников · D1

- **Подпроцессы:** заявка на роль → поиск → отбор → оффер → оформление (договор) → онбординг →
  испытательный → регулярные one-to-one/ретро.
- **Вход:** оргпотребность, штатное расписание. **Выход:** нанятый сотрудник, оформленные
  документы, план адаптации.
- **Роли:** Head of People/COO (A), нанимающий менеджер (R), Legal (C).
- **Документы:** S — Регламент найма, Профиль роли/должностная, Чек-лист онбординга; I —
  трудовой/партнёрский договор, план адаптации; C — пройденный испытательный.
- **Инвариант:** командные документы обезличиваются на выходе (направление + ответственный).

### P10 — Управление данными и метриками · D4

- **Подпроцессы:** моделирование сущности → определение метрики (формула из фактов) →
  назначение владельца/стюарда → контроль качества данных → отслеживание происхождения
  (lineage) → публикация витрины.
- **Вход:** бизнес-события (append-only), требования к KPI. **Выход:** `kpi_definitions`,
  витрины `v_*`, словари.
- **Роли:** CTO/Data (A), Data Steward (R), Analyst (C), владелец KPI (A по своей метрике).
- **Документы:** S — Политика Data Governance, Data Dictionary, Словарь метрик, Бизнес-глоссарий,
  Стандарт именования данных; I — записи lineage, отчёт качества данных; C — опубликованная
  витрина.
- **Инвариант:** единый источник истины; каждый показатель считается один раз; у метрики один
  владелец; факты append-only.

### P11 — AI-контур: промпты, агенты, оценка · D4→D5

- **Подпроцессы:** проектирование промпта/агента → версионирование → тестовый прогон → eval →
  human review → релиз → мониторинг стоимости/качества → откат при регрессе.
- **Вход:** задача (генерация отчёта, консультант, анализ сертификатов), контекст-корпус.
  **Выход:** версия промпта/агента в проде, метрики качества/стоимости.
- **Роли:** AI Engineer (R), CTO (A), Quality/eval (A по качеству), Methodologist (C).
- **Документы:** S — Политика AI, Библиотека промптов, Инструкции агентов, eval-правила,
  Стандарт human review, Политика AI-безопасности; I — версия промпта, лог eval, AI-аудит-запись;
  C — зарелиженная версия.
- **Инвариант:** AI объясняет/прогнозирует/рекомендует, но **не утверждает решения и не меняет
  KPI** (Принцип №11 канона); граница ответственности AI фиксируется явно.
