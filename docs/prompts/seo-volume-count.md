# Задание: сколько SEO-страниц портал может выдать в индекс уже сейчас

Для разработчика портала (репозиторий `mainexperts-portal`) или для сессии Claude Code в этом репозитории. Версия 1 от 13.11.2026. Основание: ТЗ `docs/22-seo-page-tree-tz.md`, образцы страниц `docs/html/seo-samples/` (архив `seo-samples.zip`). Задача только на чтение: ничего не менять, ничего не записывать в базу, персональных данных не выгружать.

## Цель

По фактической базе портала получить **разбивку по типам страниц на взаимоисключающие классы** (раздел «Классы»): сколько страниц каждого типа готовы к индексу, сколько уйдут в canonical на родителя, сколько не хватает данных для уникализации и чем именно, сколько будет оболочек, сколько не создаётся. Для типов, которые посчитать нельзя, указать причину и что нужно добавить в данные. Результат читает владелец проекта и по нему решает, что наполнять до первого выпуска.

## Классы (каждая возможная страница попадает ровно в один)

| Класс | Смысл | Что делать с адресом |
|---|---|---|
| **K1. В индекс** | пороги выполнены, данных и уникального текста достаточно | 200, `index`, canonical на себя, в sitemap |
| **K2. В индекс после уникализации** | пороги по данным выполнены, не хватает одного-двух элементов, которые мы можем добавить сами: редакционный текст ≥ 300 знаков, FAQ из агрегатов, срок подачи, подборка | 200, `noindex` до добавления; после добавления переходит в K1 |
| **K3. Canonical на родителя** | по составу данных совпадает с родителем (один вуз в городе, один город в регионе, комбинация даёт тот же список, что и родитель) | отдельной страницы нет или 200 с canonical на родителя |
| **K4. Оболочка** | все сущности существуют, но данных меньше порога (`P_prog`, `P_inst`, `P_short`) | 200, `noindex`, не в sitemap |
| **K5. Не создаётся** | нет сущности или нет ни одной программы | 404 |

Сумма пяти классов равна «возможных» по типу. Для K2 обязательно указать **причину** по каждой из категорий (нет текста, нет цены, нет срока подачи, нет FAQ-агрегата, нет языка, нет возраста и т. п.) и число страниц на каждую причину; одна страница может иметь несколько причин: считать и «страниц с причиной X», и «страниц, которым не хватает только X».

## Параметры (значения по умолчанию из ТЗ; считать для каждого из трёх сценариев)

| Параметр | Мягкий | Базовый | Жёсткий | Смысл |
|---|---|---|---|---|
| `P_inst` — мин. вузов в комбинации | 2 | 2 | 3 | |
| `P_prog` — мин. программ (и одновременно ≥ `P_inst` вузов) | 2 | 3 | 5 | |
| `P_short` — мин. актуальных коротких программ | 1 | 2 | 3 | |
| `k_pair` — соседей для пар сравнения | 5 | 5 | 3 | |
| `G_min` — вузов в радиусе геообъекта | 2 | 3 | 5 | |

## Порядок работы

**Шаг 0. Разведка схемы.** Найти, где в базе и коде лежат сущности: страна, город, вуз, колледж, программа, направление, сфера, профессия, олимпиада, подборка редактора, календарь сроков, цены, курсы. Источники: `crates/portal-search` (индекс поиска), миграции, обработчики `filter`, `panels`, `places`. Если данные живут не в SQL, а в поисковом индексе, считать через него и написать, как именно. Выписать таблицу «сущность → таблица или индекс → ключ → поля, которые нам нужны» (список полей — шаг 1). **Не угадывать имена**: что не нашёл, записать в раздел «Не найдено».

**Шаг 1. Нужные поля.** Для типов, описанных в `vault/portal-filters/Матрица доступа.html` (страна, город, регион, направление, профессия, вуз, колледж, программа, языковые школы, курсы), заполняемость уже известна (`docs/25`): сверить с матрицей только расхождения и поля, которых в матрице нет (падежи, `name_short`, возраст курсов). Для каждого поля указать: есть, нет, есть частично (и с какой долей заполнения, в процентах строк).

| Сущность | Поля |
|---|---|
| Программа | вуз, направление (или CIP-семейство), уровень, язык, форма, цена и валюта, длительность, проходной балл, бюджетные места, места для иностранцев, страна, город |
| Вуз / колледж | страна, город, тип финансирования, слаг, есть ли публичная страница |
| Страна | календарь сроков (есть ли события), флаг «редакторы выключили фильтр» |
| Редакционный контент | есть ли у страны, города, направления, профессии, вуза **собственный текст**; его длина в знаках |
| Профессия | сфера, связь с направлениями, источники (O*NET, ESCO) |
| Короткие программы, школы | есть ли такие таблицы вообще; сколько записей; заполнены ли возраст, даты, цена |
| Геоданные | есть ли координаты у стран, городов, вузов; справочники достопримечательностей, районов |
| Падежи и формы для мета-шаблонов | есть ли у стран и городов поля `name_prep`, `name_gen`, `name_to`; у языков `lang_on`; у вузов `name_short` (`docs/23`, М-5); доля заполнения |
| Язык интерфейса | какие локали реально переведены (ru, en, kk, uz, ar) и на сколько процентов |

**Шаг 2. Исходные счётчики по типам.** Для каждого типа из таблицы ниже получить: `возможных` (произведение справочников), `существует` (есть ≥ 1 программа или вуз), `проходит порог по данным` (при каждом из трёх сценариев), и для каждой страницы признаки, из которых в шаге 3 строятся классы: есть ли цена, срок подачи, уникальный текст ≥ 300 знаков, FAQ-агрегат, совпадает ли состав с родителем.

| Тип | Что считать |
|---|---|
| T01 страна | страны с ≥ 1 программой |
| T02 город | города с ≥ 1 вузом; отдельно число одновузовых городов |
| T03 вуз, T04 колледж | записи; из них с ≥ 4 заполненными блоками данных (программы, цены, сроки, FAQ-агрегаты) |
| T05 школа | число записей (если таблицы нет, так и написать) |
| T06 программа | число программ; есть ли у программы собственная публичная страница |
| T07 направление, T08 сфера | с ≥ `P_prog` программ и ≥ `P_inst` вузов |
| T09 профессия | профессии, у которых есть связанные направления; с собственным текстом |
| T10 олимпиада | число (только ru) |
| T11 короткая программа | число записей; из них с возрастом, датами и ценой; из них с датой в будущем |
| T20 направление × страна | пары (направление, страна) с ≥ `P_prog` программ и ≥ `P_inst` вузов |
| T21 направление × город | пары с ≥ `P_inst` вузов |
| T22 уровень × страна, T23 язык × страна | пары с порогом |
| T24 форма × город | пары с порогом |
| T25 бюджет до X × страна | ступени X = 1 000, 2 000, 5 000, 10 000, 20 000 USD в год; страны с порогом программ ≤ X |
| T26 профессия → где учиться | пары (профессия, страна) через направления профессии, с порогом |
| T27 короткие: тема × страна × период (месяц) × возраст (диапазоны 10–13, 14–17) | комбинации с ≥ `P_short` актуальных программ; если коротких программ нет, 0 и причина |
| T30 маршрут «откуда → куда» | страны «откуда» = рынки портала (список из виджета) × страны «куда» × направление × уровень; оболочки только там, где у страны назначения есть хотя бы одна программа по направлению и уровню; из них материализуемые по порогу T20 |
| T43 страница из выбранных фильтров | допустимые наборы фасетов из `docs/22` R-4.3.3 (страна+направление; страна+уровень; страна+язык; страна+направление+уровень; +язык; +уровень+язык; +«бесплатно»; город+направление): по каждому набору произведение числа значений фасетов, затем пороги. Пары, совпадающие с T20–T26, не считать повторно |
| T34–T36 происхождение × город, вуз, программа (`docs/22`, 4.5) | страны отправления с собственными данными пары (виза, цена под гражданство) × назначения с программами; число пар, проходящих R-4.5.4, по уровням назначения; число стран отправления с заполненными «виза» и «цены под гражданство» |
| T40 пара «A или B» | по каждому типу (вуз, программа): `n`, `n·k_pair`, из них при `k_pair` = 5 и 3. Близость: пересечение направлений, один регион, цена в одном диапазоне (описать, как посчитал) |
| T41 набор 3–5 | не считать, только перечислить, какие кураторские фильтры уже есть в редакторской части |
| T50–T53 геостраницы | сколько объектов с координатами; сколько вузов с координатами; число пар «объект ↔ вуз» в радиусе 5 км при `G_min` = 3 (если координат нет, 0 и причина) |

**Шаг 3. Разбивка по классам.** По каждому типу для базового сценария заполнить строку: возможных → K1 → K2 → K3 → K4 → K5 (сумма K1…K5 = возможных). Дополнительно: «в sitemap» = K1. Затем разбивка K2 по причинам (таблица: тип × причина × число страниц × число страниц, которым не хватает только этой причины). Доли «ожидаемо в индексе» не заполнять: их знает только вебмастер после запуска.

**Шаг 4. Чувствительность.** Для T20, T21, T22, T23, T26 вывести число страниц при каждом значении `P_prog` ∈ {1, 2, 3, 5, 10}. Нужно, чтобы владелец увидел, где порог «ломает» объём.

**Шаг 5. Проверка слепых зон.** Ответить коротко:
1. Сколько страниц получит `noindex` из-за отсутствия цены, срока подачи или текста.
2. Сколько комбинаций дублируют родителя (один вуз в городе, один город в регионе).
3. Сколько адресов уже живут в портале и как они закрыты от индекса (`/find` и фильтры: `noindex, follow`, canonical без фильтров — подтвердить по коду).
4. Есть ли уже sitemap и сколько в нём URL; какие типы в нём.
5. Какие локали реально переведены.

## Формат результата

Один файл `seo-volume-report.md`:

1. Шапка: дата, коммит базы или кода, СУБД и способ счёта.
2. Таблица полей (шаг 1): есть / нет / частично, доля заполнения.
3. **Главная таблица — разбивка по типам и классам** (шаг 3): строка на тип T01…T53, столбцы возможных, K1, K2, K3, K4, K5; базовый сценарий; ниже две такие же таблицы для мягкого и жёсткого сценариев.
4. Таблица причин по K2 (тип × причина × страниц × страниц «только с этой причиной»).
5. Таблица чувствительности (шаг 4).
6. Ответы на слепые зоны (шаг 5).
7. Не найдено и допущения.
8. Приложенные запросы: каждый запрос текстом, чтобы число можно было воспроизвести.

Числа без запроса не принимаются. Если счёт невозможен, писать «не посчитано: причина и что нужно добавить в данные», не оценивать на глаз.

## Пример запроса (Postgres; имена условные, подставить реальные)

```sql
-- T20 направление × страна при P_prog и P_inst
SELECT count(*) AS pages
FROM (
  SELECT i.country_iso2, p.field_id,
         count(*) AS n_prog, count(DISTINCT p.inst_id) AS n_inst
  FROM program p JOIN institution i ON i.id = p.inst_id
  GROUP BY 1, 2
  HAVING count(*) >= :p_prog AND count(DISTINCT p.inst_id) >= :p_inst
) t;

-- T21 направление × город при P_inst
SELECT count(*) FROM (
  SELECT i.city_id, p.field_id
  FROM program p JOIN institution i ON i.id = p.inst_id
  GROUP BY 1, 2 HAVING count(DISTINCT p.inst_id) >= :p_inst) t;

-- T40 пары: верхняя граница при k_pair
SELECT count(*) * :k_pair AS pairs_upper FROM institution;
```

## Ограничения

- Только чтение. Не менять код, не писать в базу, не запускать импорт.
- Не выгружать персональные данные пользователей: нужны только агрегаты по справочникам.
- Не выдумывать числа и названия таблиц; не найденное фиксировать в разделе «Не найдено».
- Не использовать названия методик BFAS/Big Five и RIASEC в отчёте; параметр `riasec` называть «тип работы».
- Результат вернуть владельцу проекта как есть, без решений о том, что включать в индекс: решения принимаются по таблицам после сверки с вебмастером.

## Что остаётся посчитать после матрицы

Матрица даёт знаменатели и заполняемость по одному параметру, но не совместное наличие. Остаются счёты по парам и комбинациям: сколько пар «из X в Y» и сколько комбинаций «страна × направление × уровень × язык» имеют программы; сколько стран отправления имеют заполненные «виза» и «цены под гражданство»; сколько программ имеют одновременно описание и цену; как «12 направлений» матрицы соотносятся со справочником направлений базы.

## Режим контента (`docs/22`, раздел 4.4)

Для типов T30, T31, T43 и T01 с «в» и «из» база нужна только как булево «есть ли программы для комбинации» и как справочники. Дополнительно посчитать: число стран отправления (рынки портала); число допустимых пар «из X в Y», где в базе есть программы; число комбинаций «пара × направление × уровень × язык», для которых программы есть; число распространённых лет набора, для которых есть даты набора или календарь страны. Причины K2 для этих типов — отсутствие редакционных блоков (по фасету), а не недостаток данных базы.

## Что вернуть в чат

Главную таблицу целиком (тип × K1…K5, базовый сценарий) и под ней по одной строке: итого K1; итого K2 и три главные причины; что мешает посчитать (если мешает).
