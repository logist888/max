# Задание Даниилу: полный подсчёт, данные кабинета, проверка уникальности и мета на реальных данных

Версия 2 от 13.11.2026. В сборку Даниила влиты коммиты Сергея, поэтому у неё полная база по всем направлениям: это самое широкое из заданий. Состоит из шести частей: (1) полный подсчёт объёма по всем типам страниц, (2) данные кабинета и сборки Даниила (короткие программы, закладки, сравнения, профиль, языки), (3) проверка уникальности страниц на реальных данных, (4) прогон мета-шаблонов на реальных данных, (5) список полей, которые надо добавить в базу, (6) защита выдачи. Только чтение базы и кода приложения: приложение не менять, в базу не писать, импорт не запускать. Допускается создавать скрипты и файлы отчёта в папке `seo-task/`. Персональных данных не выгружать: нужны только агрегаты.

## Порядок и приоритеты

Выполнять по частям и после каждой сохранять промежуточный отчёт (файл `seo-volume-report-daniil.md` дополняется): если время кончится, готовые части уже можно читать. Приоритет: часть 1, затем 2.B (закладки), затем 3, затем остальное.

## Шаг 0. Проверка базы

Подтвердить письменно (первый пункт отчёта): в сборке слиты коммиты Сергея, база программ, вузов, городов, стран полная; указать версию кода (коммит), дату снимка данных, СУБД или индекс. Если что-то из типов `docs/22` отсутствует в схеме, записать в «Не найдено».

## Часть 1. Полный подсчёт объёма по всем типам

Выполнить задание `00-ЗАДАНИЕ-seo-volume-count.md` целиком: шаги 0–5, три сценария порогов, классы K1…K5, причины K2, чувствительность по `P_prog`, происхождение × назначение (T30, T31, T34–T36), слепые зоны. Результат — раздел 1 отчёта в формате того задания.

## Часть 2. Данные, которых нет в дереве Сергея (кабинет и сборка Даниила)

Разделы A…D ниже.

## A. Короткие программы и курсы (T11, T27)

Найти, где хранятся короткие программы (по концепту: формат, период и даты, тема, длительность, возраст на старте). По вашей базе получить:

| Показатель | Что дать |
|---|---|
| Записей всего | число; сверить с цифрой матрицы: 85 677 курсов в базе портала |
| Заполненность | доли записей с возрастом (минимум и максимум), датами старта и окончания, ценой и валютой, форматом (очно, онлайн, смешанно), темой, длительностью, городом, провайдером |
| Актуальные | сколько с датой старта в будущем; по месяцам 2027 года |
| Летние школы | сколько; из них с датами и ценой |
| T27 | число комбинаций «тема × страна × месяц × возрастной диапазон (10–13, 14–17)» с ≥ 1, ≥ 2, ≥ 3 актуальных программ |
| Тема | как хранится (справочник, свободный текст, теги); сколько различных значений |

Если возраст указан у малой доли (в матрице 2 %), прямо сказать, сколько страниц T27 с возрастным фасетом возможно и сколько без него.

## B. Закладки, сравнения, лайки (T40, T41, T42 вид в)

Цель: понять, достижим ли порог «N независимых пользователей» для публичных подборок (`22`, R-7.10: умолчание N = 50). **Только агрегаты, без идентификаторов пользователей.**

1. Где хранятся закладки и сравнения: на сервере (в какой таблице) или только в браузере. Если только в браузере, сказать и закончить раздел.
2. Для каждой сущности (вуз, программа, курс, страна, направление): число различных пользователей, добавивших в закладки. Распределение: сколько сущностей имеют ≥ 5, ≥ 10, ≥ 20, ≥ 50 различных пользователей.
3. Сравнения: сколько различных пар «A и B» сравнивали ≥ 5, ≥ 10, ≥ 20, ≥ 50 различных пользователей; то же для наборов из 3–5.
4. Сколько всего пользователей с хотя бы одной закладкой; сколько из них отмечены как подростки 10–18 лет (если возраст хранится) — только число.
5. Есть ли защита от накрутки (лимиты на устройство, адрес, возраст аккаунта) и как проверяется независимость.

Не выгружать строки пользователей, адреса почты, имена и идентификаторы. Только числа и распределения.

## C. Профиль подбора, слежение за сроком, совпадение в процентах

Для каждой из функций: есть ли в сборке; где данные; что из этого может быть публичным без идентификации (например, «число людей, следящих за сроком подачи в страну X»; публичны ли такие агрегаты; есть ли порог показа). Ничего публичного из данных ребёнка не предлагать: цель — понять, какие агрегаты вообще существуют.

## D. Язык интерфейса и справочники падежей

1. Какие локали реально есть в сборке (ru, en, kk, uz, ar) и на сколько процентов переведены строки интерфейса по каждой; где лежат файлы (формат, путь).
2. Есть ли поля форм слов в справочниках (`name_prep`, `name_gen`, `name_to`, `lang_on`, `name_short`) или их аналоги; доля заполнения.
3. Как обрабатываются множественные числа (библиотека, правила для русского и английского).
4. Как хранится язык пользователя и рынок (cookie `market`, `currency`): независимы ли они (`24`, Л-2).
5. Поддерживается ли правосторонняя вёрстка (арабский).

## Часть 3 (E). Проверка уникальности на реальных данных

Цель: проверить на настоящей базе порог `U_share = 40 %` (`22`, R-4.4.5): доля одинаковых предложений между соседними страницами режима контента.

1. Выбрать выборки: (а) 30 пар «из страны X в страну Y» (страны отправления — первые по числу пар с данными; назначения разные); (б) для двух фиксированных пар по 8 страниц-фасетов (уровень × язык × год набора, как в образцах `route-de-it-*`); (в) по 30 страниц типов T02, T03, T20, T21, T35 и T36; (г) 30 страниц программ, у которых есть описание.
2. Собрать текст страниц **по правилам режима контента** (`22`, R-4.4.1: данные D1, без перечней записей и без полей с ✕ или ◐ для робота в матрице `25`). Блоки данных (виза, цены под гражданство, стоимость жизни, стипендии, сроки подачи, числа, диапазоны цен) брать из базы; редакторские блоки подставить как заглушки одинаковой длины и помечать отдельно (они не должны влиять на оценку данных).
3. Для каждой пары соседних страниц посчитать долю одинаковых предложений (предложения ≥ 25 знаков; отношение пересечения к объединению; отдельно по блокам данных и по всей странице). Дать распределение по каждому типу: медиана, 90-й процентиль, доля пар выше 40 %.
4. Вывод: какие типы проходят порог только за счёт данных базы, какие требуют редакторских блоков, какие не проходят ни так, ни так (кандидаты на canonical или `noindex`).
5. Приложить скрипт и 10 примеров собранных страниц (без персональных данных).

## Часть 4 (F). Прогон мета-шаблонов на реальных данных

Цель: проверить `23-seo-meta-templates.md` на данных.

1. Для выборки из 1 000 страниц на тип (T01, T02, T03, T06, T20, T21, T23, T30, T34, T35, T43) собрать `title`, `description`, `h1` по шаблонам раздела 4 (основные, с числами; запасные из 4.7, если число недоступно).
2. Проверить М-А1…М-А8: длины (en ≤ 60, ru ≤ 55 цель; 70 и 180 предел), пустые поля, дубли `title` и `description` среди страниц, склонение чисел (1, 2, 5, 11, 12, 21, 22, 25, 111), отсутствие значений D0.
3. Дать таблицу: тип × доля страниц с корректными мета; по причинам отказа (нет `name_prep`, длина, дубль, нет данных).
4. Приложить скрипт и 20 примеров на каждом языке (ru, en), если английские названия есть.

## Часть 5 (G). Что добавить в базу и код

Список полей и справочников, которых не хватает для запуска, по убыванию влияния на число страниц K1: поле, сущность, доля заполнения сейчас, сколько страниц (K2, K4) оно разблокирует, трудоёмкость (малая, средняя, большая: оценка разработчика, не выдумывать, помечать «оценка»). Минимум: падежи и `name_short`; данные по городам отправления; описание программ; возраст курсов; даты набора по годам; поле «число независимых пользователей» для подборок (если вид в будет включён).

## Часть 6 (H). Защита выдачи

Страницы-маршруты ведут на `/find`. Описать: лимиты запросов и проверка ботов на `/find` и обработчиках `filter`, `panels`, `places`; глубина выдачи (1 000); возможна ли выгрузка записей перебором параметров; чего не хватает до публикации миллионов страниц-маршрутов. Не менять, только описать и дать оценку риска.

## Формат результата

Файл `seo-volume-report-daniil.md` (дополняется по мере выполнения):

1. Шапка и шаг 0: дата, коммит, СУБД, способ счёта.
2. Часть 1: полный отчёт по `00-ЗАДАНИЕ-seo-volume-count.md` (главная таблица, причины K2, чувствительность, происхождение × назначение, слепые зоны).
3. Часть 2: разделы A, B, C, D.
4. Часть 3 (E): таблицы уникальности по типам и выводы.
5. Часть 4 (F): таблицы корректности мета.
6. Часть 5 (G): список полей по влиянию.
7. Часть 6 (H): описание защиты выдачи.
8. Не найдено и допущения.
9. Запросы и скрипты: приложены отдельными файлами в `seo-task/`.

Правила: числа без запроса не принимаются; не угадывать имена таблиц; чего нет, так и написать («не найдено»), не оценивать на глаз; названия методик BFAS/Big Five и RIASEC в отчёте не использовать.

## Что вернуть в чат

Семь строк: (1) итоговая таблица K1…K5 по типам, базовый сценарий (целиком или ссылка на раздел); (2) число пар «страна → страна» с ≥ 2 блоками данных; (3) сколько актуальных коротких программ и сколько с возрастом; (4) сколько сущностей и пар достигают 50 независимых пользователей; (5) какие типы проходят `U_share = 40 %` на реальных данных; (6) доля страниц с корректными мета; (7) три главных недостающих поля из части 5.
