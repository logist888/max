# 00. Каркас борда (Dashboard Framework)

> Источник: MainExperts Management System (MMS), Том II «Functional Specification» (вер. 1.0), Предисловие + Глава 1 «Общие требования» + Глава 3 «Dashboard Framework»; снимок 27.06.2026;
> Google Drive / MainExperts (`1.pdf` Том I, `2.pdf` Том II; владелец agafonov.agency,
> загр. 27.06.2026). Рабочий контекст — перед клиентскими материалами перепроверять с источником.

Каркас задаёт единые правила, по которым строятся все управленческие борды (Dashboard) системы. Каждый борд состоит из одинаковых элементов и подчиняется общим требованиям к производительности, фильтрации, детализации (Drill Down), экспорту и объяснению (AI Explain). Этот файл — спецификация общего слоя; конкретные борды — Owner (L0) и шесть функциональных (Финансы, Маркетинг, Продажи, Операции, Экспертная сеть, Продукты) — наследуют его и не переопределяют. Полный реестр бордов — в [обзоре системы](../08-board-system.md).

## Место в системе

MMS автоматизирует управление компанией через централизованное хранение данных, автоматический расчёт KPI, визуализацию состояния бизнеса, поддержку принятия решений, AI Copilot и контроль исполнения решений. Борды — слой визуализации в общей архитектуре потока данных (см. ниже): они получают рассчитанные показатели от KPI Engine и подают их в AI Copilot и далее в управленческие решения.

Документ Functional Specification — основной для ролей: Product Owner, Business Analyst, Solution Architect, Backend Team, Frontend Team, BI Team, Data Engineers, QA, DevOps, AI Team. Все его требования обязательны при реализации.

## Принципы проектирования

При разработке системы соблюдаются пять принципов (Глава 1.3).

| Принцип | Содержание |
| --- | --- |
| Single Source of Truth | Любой показатель рассчитывается только один раз. |
| Event Driven | Все изменения начинаются с событий. |
| KPI Driven | Интерфейсы проектируются вокруг KPI. |
| Decision Driven | Все элементы интерфейса должны помогать принимать решения. |
| AI First | Каждый новый модуль оценивается с точки зрения возможности использования AI. |

## Общая архитектура потока данных

Поток данных проходит фиксированную последовательность слоёв (Глава 1.4):

```
Business Events
  ↓ Raw Data
  ↓ Business Objects
  ↓ KPI Engine
  ↓ Dashboards
  ↓ AI Copilot
  ↓ Management Decisions
```

> Оговорка из источника: ни один уровень не должен обращаться напрямую к предыдущему, минуя архитектурные слои.

## Анатомия борда

Все управленческие интерфейсы строятся по единым правилам; каждый Dashboard состоит из одинаковых элементов (Глава 3.1).

| Элемент | Назначение |
| --- | --- |
| Header | Название; Период; Фильтры; Экспорт; AI. |
| KPI Cards | Главные показатели. |
| Trends | Динамика. |
| Alerts | Отклонения. |
| Drill Down | Причины. |
| Actions | Рекомендуемые действия. |

> Пробел: в исходнике не раскрыто — внутренний состав блоков Trends и Actions (Глава 3.1 перечисляет блоки без детализации их содержимого).

## Общие требования к борду

Каждый Dashboard обязан (Глава 3.2):

- открываться менее чем за две секунды;
- поддерживать фильтрацию;
- поддерживать Drill Down;
- поддерживать экспорт;
- поддерживать AI Explain.

## Иерархия бордов (L0–L3)

Все Dashboard делятся на уровни (Глава 3.3).

| Уровень | Состав |
| --- | --- |
| L0 | Owner Dashboard. |
| L1 | Финансы; Маркетинг; Продажи; Продукты; Эксперты; AI. |
| L2 | Подробные операционные борды. |
| L3 | Карточки объектов. |

> Пробел: в исходнике не раскрыто — поимённый перечень бордов уровня L2 и L3 (даны только обобщённые названия уровней).

> Расхождение источника: список L1 в Главе 3.3 («Финансы; Маркетинг; Продажи; Продукты;
> Эксперты; AI») не совпадает с фактическим составом глав раздела III — там есть Operations
> (гл. 8), но нет главы об отдельном AI-борде. Метрики AI раскрыты внутри Owner Dashboard
> (блок AI, гл. 4.10) и Operations (AI Capacity, гл. 8.15). Зафиксировано, не разрешено;
> канон следует составу глав (семь бордов).

## Общие элементы KPI Card

Каждая карточка KPI должна содержать (Глава 3.4):

- Название;
- Текущее значение;
- План;
- Отклонение;
- Тренд;
- Цвет статуса;
- Ссылку на Drill Down;
- AI Explain;
- Историю изменений.

Конкретные борды наследуют этот состав карточки и не переопределяют его.

## Общие правила Drill Down

Любой KPI раскрывается одинаково — по фиксированной последовательности уровней (Глава 3.5):

```
KPI
  ↓ Dimension
  ↓ Subdimension
  ↓ Object
  ↓ Primary Event
```

Пользователь не может пропустить уровень.

## Общие правила Alerts

Каждый Alert содержит (Глава 3.6):

- Заголовок;
- Причину;
- Влияние;
- Ответственного;
- Playbook;
- AI Explanation;
- Кнопку перехода.

> Пробел: в исходнике не раскрыто — пороги срабатывания, сортировка по критичности и связь Alert → Playbook как процесс (Глава 3.6 описывает только состав Alert).

## AI Explain

Каждый Dashboard имеет кнопку AI. После нажатия пользователь получает (Глава 3.7):

- краткое описание;
- основные изменения;
- причины;
- риски;
- рекомендации;
- связанные KPI.

> Пробел: в исходнике не раскрыто — граница ответственности AI (что AI не утверждает решения и не меняет KPI). В выданном срезе этот общий принцип явно не сформулирован — приведённый в шаблоне бордов тезис здесь источником не подтверждается.

## Производительность

| Функция | Требование |
| --- | --- |
| Открытие борда | Менее двух секунд (Глава 3.2). |

> Пробел: в исходнике не раскрыто — иные требования к производительности (отклик фильтров, раскрытие Drill Down, экспорт). Детальные нефункциональные требования отнесены к разделу XIII «Non-Functional Requirements», вне извлечённого текста.

## Граница раздела

Главы 1 и 3 определяют единые требования ко всем интерфейсам системы. Следующая глава источника описывает первый и наиболее важный экран — Owner Dashboard: полный состав, бизнес-логику, структуру данных, правила отображения, сценарии использования и критерии приёмки.

> Пробел: Глава 2 в выданном срезе отсутствует (срез — Предисловие + Глава 1 + Глава 3); раздел II «Пользователи и роли» и прочие разделы Functional Specification вне извлечённого текста.
