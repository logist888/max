# SYSTEM.md — устройство системы обработки и хранения

Назначение: принимать длинные файлы (20–50 стр.) по MainExperts, превращать их в
связное хранилище знаний (по образцу Obsidian) и собирать из него отчёты.
Поведение — в `CLAUDE.md`. Факты — в `memory/memory.md` и `vault/`.

## Что это технически (без иллюзий)
Это не отдельный высоконагруженный сервис. Высокая нагрузка проекта — на боевой
платформе (Rust, 50–100К пользователей), это другой контур. Здесь «нагрузка» —
поток длинных документов против ограниченного окна модели. Решение: один раз
дистиллировать файл в атомарные заметки, дальше работать с заметками, а не с
сырьём. Узкое место — не диск, а контекст; хранилище его разгружает.

## Два контура хранения
- **Репозиторий (git)** — движок и хранилище: код, скиллы, канон `docs/`, рабочие
  заметки `vault/`, снимок памяти. Полный доступ: создание, правка, удаление,
  история. Вся работа идёт здесь.
- **Google Drive, папка MainExperts** — канон и витрина: эталон `memory.md` и
  готовые отчёты (PDF). Drive не умеет удалять/переименовывать/перезаписывать и не
  рендерит вики-ссылки — потому хранилище живёт в git, а в Drive уходят снимки и
  результаты.

## Среда эфемерна
Контейнер пересоздаётся, репозиторий клонируется заново, установленные пакеты не
сохраняются. Отсюда: всё ценное — коммитить и пушить; зависимости ставить при
загрузке (`scripts/setup.sh`); канон памяти держать и в git (снимок), и в Drive
(эталон).

```
docs/                КАНОН знаний (кураторский): 01-strategy … 07-principles
  private/           поток-1 (HNW) — конфиденциально, вне git
reference/           оригиналы методологий (V4.1, Федоренко, схема процесса, инструкция)
memory/memory.md     дословный снимок канонической памяти с Drive
vault/               РАБОЧИЕ заметки из новых ингестов
  00-index/MOC.md    карта содержания — точка входа в хранилище
  00-index/tags.md   контролируемый словарь меток
  _templates/        шаблоны заметок (source/note/entity/report)
  10-sources/        по одной заметке на загруженный файл (метаданные+конспект, НЕ сырьё)
  20-notes/          атомарные заметки (одна мысль), связаны вики-ссылками
  30-entities/       сущности: персонажи ЦА, концепции, профессии, команда
  40-reports/        черновики отчётов до экспорта в Drive
raw/                 архив сырья — не индексируется, грузится по нужде
scripts/             extract.py, pdf_ru.py, setup.sh, requirements.txt
.claude/skills/      boot, ingest, report
```

## Модель заметки (frontmatter)
Каждая заметка начинается YAML-шапкой:
```
---
id: 2026-06-23-1430-nazvanie       # время создания + kebab-заголовок, уникален
type: source | note | entity | report
title: ...
created: 2026-06-23
updated: 2026-06-23
stream: поток-1 | поток-2 | общее              # ОБЯЗАТЕЛЬНО; потоки не смешивать
goal: валидация | гипотеза-скрининга | опыт | н/д   # для темы привлечения экспертов
status: факт | гипотеза | требует-проверки     # вывод на гипотезе скрининга = «гипотеза»
source: "[[10-sources/<id>]]"                  # происхождение
source_ref: "<файл>, стр. N"
source_date: 2026-06-22
source_url: <ссылка Drive/url>
tags: [riasec, big-five]
links: ["[[...]]"]
---
```
**Правило премиум-факта:** заметка с фактическим утверждением обязана нести
`source_ref` + `source_date` + `source_url`. Нет источника — `status: требует-проверки`,
в отчёт не идёт.

## Хранение (как класть) — скилл `ingest`
Загруженный файл → текст (Drive MCP или `scripts/extract.py`) → разметить разделы → сверить с каноном `docs/` → создать:
1. одну `source`-заметку (метаданные + конспект + карта разделов, без полного текста);
2. N атомарных `note`-заметок (одна мысль своими словами, с происхождением);
3. обновить `entity`-заметки (персонажи, концепции, профессии, команда);
4. проставить вики-ссылки между заметками и в `MOC.md`;
5. сырьё положить в `raw/`.

## Загрузка (как доставать)
Сырьё не грузить. Порядок: канон `docs/01–07` + `vault/00-index/MOC.md` → при
необходимости свежие `vault/`-заметки и дословный `memory/memory.md` (поиск `rg` по
`docs/` и `vault/`, переход по `[[ссылкам]]`) → грузить только нужное. Сырьё из
`raw/` — лишь когда заметок недостаточно. Беречь контекст: канон и заметка вместо
сырья, по требованию.

## Отчёты — скилл `report`
Выбрать охват + поток + персонажа (Ольга/Инесса/Андрей/Валерий) → собрать из канона
`docs/` и свежих заметок `vault/` → прогнать жёсткие правила → черновик в `40-reports/` → экспорт в
кириллический PDF (`scripts/pdf_ru.py`) → доставка в Drive. Структура — в
`vault/_templates/report.md`, посеяна из памяти (четыре голоса; разделы скрининга;
«сначала неудобная находка»). **Эталон формата калибруется по первому образцу Игоря.**

## Как система держит жёсткие правила
- **Потоки:** поле `stream` обязательно; `report` отказывается смешивать метрики
  поток-1 и поток-2.
- **Гипотеза скрининга:** выводы на ней — `status: гипотеза`; отчёт ставит
  стандартную оговорку о невалидированности.
- **Переименование тестов:** BFAS/RIASEC в клиентских материалах — только рабочие
  имена (см. `vault/30-entities`).
- **Данные:** премиум-факт без источника не покидает хранилище.
- **Обезличивание:** имена допустимы в `vault`, но `report` заменяет их на
  направление + ответственный в скобках.

## Синхронизация с Drive
При обновлении памяти: создать новый `memory_vГГГГ-ММ-ДД.md` в папке MainExperts,
обновить снимок `memory/memory.md`, указать Игорю, какой прежний файл удалить
вручную. Держать в Drive ровно две версии: актуальная + предыдущая.
