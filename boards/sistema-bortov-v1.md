## 1. Карта уровней L0→L4

Система строится **сверху вниз** (скелет Федоренко: миссия → 7 разрезов целей → PDCA) и **просчитывается снизу вверх** (дерево DuPont: микро-карточка человеко-часа эксперта → корневой светофор компании). Ровно пять уровней, каждый вложен в предыдущий. Вложенность реализуется механикой «сводка → drill-down» — прямая речь Макса: «верхнеуровневая состоит из трёх-четырёх нижнеуровневых… коробочки вложенности — нажимаешь, хоп, там больше таблиц, разъехалось».

**L0 — Стратегический финансовый контур (макро).** Один экран жизнеспособности всей компании. Корневая карточка `L0` — спред `ROI − стоимость капитала` (золотое правило: «если ROI ниже стоимости капитала… будущего этой компании нет»), единый светофор всей системы. Держит три горизонта вложенно: $1 млн → 100 млн → миллиард («миллион — промежуточная цель… идя к миллиарду, миллион я достигну»). Сюда сводятся итоги нижних ярусов — **раздельно по потокам**, единая цифра допустима ТОЛЬКО на этом агрегате.

**L1 — Процессные борты (мезо).** Шесть бортов, каждый сидит ровно на одном пути V4.1 и одном разрезе Федоренко: `L1-FIN`, `L1-M`, `L1-OPS`, `L1-PRD`, `L1-BTL`, `L1-RISK`. Каждый — «верхнеуровневая сводка», распаковываемая в эпики.

**L2 — Эпики.** Крупная связная задача внутри борта со своим результатом, сроком, агрегатом план/факт и PDCA-петлёй.

**L3 — Задачи-карточки.** Атомарная единица управления с метрикой план/факт, ответственным, DoD. Строго по схеме процесса (§3).

**L4 — Подзадачи / чек-пункты.** Атомы исполнения; измеримость через бинарный DoD.

**Два потока — ортогональная ось ко всем уровням.** Поток — это «цвет» карточки, уровень — её «высота». Каждый денежный объект на каждом уровне существует в двух экземплярах (Поток 1 / Поток 2) и сводится только верхним агрегатом `L0`. **Конечный автомат единицы работы (отчёта) — атрибут карточки `L3-BTL-01`, не шестой ярус.**

### Прослеживаемость макро↔микро по двум осям (обязательна)

- **Ось ПРИБЫЛЬ:** `L4-FIN-CM-01-01` (CM на человеко-час) → суммируется в рентабельность реализации `L2-FIN-CM` (L1) → × оборачиваемость = ROA → ROTA/ROE/ROI → спред к стоимости капитала `L0`. Карточка человеко-часа эксперта прослеживается до корневого светофора.
- **Ось ЛИКВИДНОСТЬ:** дни запасов/WIP (`L4-BTL-01-01`/`L4-BTL-01-03`) порождаются **узким местом** — экспертной проверкой отчёта (этап 5) `L2-BTL-01` → удлиняют цикл `L2-FIN-WC` → бьют в кассовый разрыв `L0`. Узкое место материализуется как финансовый показатель.

### Эталонная сквозная вертикаль (обязательный артефакт)

`L0` (спред ROI−СК) ◀ `L1-BTL` (борт узкого места) ◀ `L2-BTL-01` (эпик «очередь под пропускную вебинара») ◀ `L3-BTL-01` (карточка единицы работы — отчёт) ◀ `L4-FIN-CM-01-01` (CM на человеко-час эксперта по Профилю 360). Пересчёт: изменишь CM/час или длину очереди на L4/L3 → throughput и дни WIP на L2 → цикл оборотного капитала и contribution на L1 → спред ROI−СК и кассовый разрыв на L0. Сквозная вертикаль кодируется полем `parent_id` (см. sweep_objects).

## 2. Эталонная сквозная вертикаль и примеры карточек

Одна непрерывная цепочка drill-down на реальном объекте MainExperts: **CM на человеко-час эксперта по Профилю 360 (L4) → карточка единицы работы — отчёт (L3) → эпик «очередь экспертной проверки» (L2) → операционный борт узкого места L1-BTL (L1) → спред ROI−СК L0.** Все пять карточек заполнены по схеме §5 и связаны полем `parent_id`. Снизу идёт пересчёт метрики вверх по двум осям (прибыль / ликвидность).

### ASCII-дерево вертикали (на контрактных ID)

```
L0  Спред ROI − СК  (сводный корневой светофор)
└── L1-BTL  Операционный борт узкого места (этап 5)        [parent: L0]
    └── L2-BTL-01  Эпик «Очередь экспертной проверки»      [parent: L1-BTL]
        └── L3-BTL-01  Карточка единицы работы — отчёт П360 [parent: L2-BTL-01]
            └── L4-FIN-CM-01-01  CM/час эксперта по П360     [parent: L3-BTL-01]
                  ▲ ось прибыль:  CM/час → рент-ть реализации L1 → ×оборачив = ROA → ROTA/ROE/ROI → спред L0
                  ▲ ось ликвидн.: дни WIP → цикл оборотн. капитала → кассовый разрыв L0
```

Ортогональная ось «два потока» — здесь вся вертикаль сидит в **Потоке 2** (воронка; единица = отчёт по клиенту Профиля 360); тот же скелет существует во втором экземпляре для Потока 1 (пакеты HNW) в раздельной таблице и сводится только на L0.

### Пересчёт метрики снизу вверх (как Δ CM/час на L4 доходит до светофора L0)

Живая модель: меняем вход на L4 — пересчёт идёт вверх по двум осям. Числа ниже помечены `[иллюстрация механики, не факт MainExperts]`, стрелки и формулы — реальные.

**Ось ПРИБЫЛЬ (L4 → L0):**

```
L4  CM/час эксперта по П360 = (выручка отчёта − перем. затраты) / часы на отчёт
        Δ: часы на отчёт 4 ч → 3 ч (сократили правки)  ⇒  CM/час  +33%   [иллюстрация]
   ▼
L3  больше отчётов с того же фонда часов → растёт вклад, отнесённый на единицу работы
   ▼
L1  рентабельность реализации = Σ CM по продуктам / выручка  ↑   (статья «маркетинг» из L1-M тоже сюда — через ДРР)
   ▼
L1  ROA = рентабельность реализации × оборачиваемость активов   ↑
   ▼
L0  ROTA/ROE/ROI  ↑   ⇒   спред (ROI − СК)  растёт   ⇒   светофор L0: 🔴→🟡→🟢
```

**Ось ЛИКВИДНОСТЬ (L4/L3 → L0):**

```
L3  время отчёта в системе ↓ (короче очередь и правки)
   ▼
L1  дни WIP узкого места ↓   ⇒   цикл оборотного капитала короче
   ▼
L0  деньги быстрее возвращаются (КТ3 ближе к КТ2; предоплата на задачу обнуляет Debtors Days)
        ⇒  кассовый разрыв сокращается (сумма дефицита ₽ ↓)  ⇒  кассовый светофор L0: 🔴→🟢
```

Обратный ход (предупреждение, не симметрия): рост **доли правок** или **90-го перцентиля** на L1-BTL → падает throughput → удлиняется время в системе → одновременно ↓CM/час (часы на отчёт растут) **и** ↑дни WIP. Узкое место бьёт по обеим осям сразу: гасит прибыль и раздувает кассовый разрыв. Это и есть зашитое противоречие $1 млн через воронку (см. L1-BTL).

Каждая карточка любого уровня = шесть элементов схемы процесса (входы / выходы / регулирующие воздействия / ресурсы / показатели / ответственные) + алгоритм (статус + контрольная точка). **Инвариант: нет метрики план/факт (или бинарного DoD на L4) — нет карточки.**

| Поле | Содержание | Обязательность по уровням |
|---|---|---|
| **card_id** | Идентификатор: префикс уровня + код борта/потока + номер (`L0`, `L1-BTL`, `L2-BTL-01`, `L3-BTL-01`, `L4-FIN-CM-01-01`). | Все уровни |
| **Название** | Глагол + объект, по-русски, онтологический вектор, без штампов. | Все |
| **Уровень** | L0 контур / L1 борт / L2 эпик / L3 задача / L4 подзадача. | Все |
| **parent_id** | `card_id` карточки уровнем выше — для drill-down и трассировки вверх. | Все, кроме L0 |
| **Поток** | 1 (HNW) / 2 (воронка) / сводный (только L0). | L0–L3 обязательно для денежных; **денежная L4 — тоже несёт Поток** |
| **Путь V4.1** | клиент / заказ / исполнение / деньги / риск / данные — ровно один, кросс-загрязнение запрещено. | L0–L3 (наследуется на L4) |
| **Разрез Федоренко** | финансы / продукт / кадры / клиент / рынок / безопасность / качество. | L0–L3 |
| **Направление + ответственный** | development (Саша) / methodology (Вадим) / product (Вадим) / operations (Александр) / marketing (Игорь) / payments (Даниил) / founder (Макс); валидатор бенчмарков L0 — Илья. | L0–L3 |
| **Статус** | из словаря §4 (канбан или PDCA). | Все |
| **Входы** | данные, событие, заявка, час эксперта, бюджет. | L0–L3 |
| **Выходы** | отчёт, продажа, оплата, профиль. | L0–L3 |
| **Регулирующее воздействие / риск** | НПА, стандарт, лицензия, узкое место, гипотеза-ставка — то, на что процесс повлиять НЕ может. Маркеры `⚠ СТАВКА` / `🔴 РЕГУЛЯТОР` / `⛔ УЗКОЕ МЕСТО`. **Обязательно для карточек с данными детей и психомодулями.** | L0–L3; на L4 — если касается риска |
| **Ресурсы** | человеко-часы эксперта, бюджет, инструмент, серверы/Anthropic, код-база на Rust. | L0–L3 |
| **Метрика (план / факт)** | показатель, формула, план, факт, Δ, единица. **Без неё карточка невалидна.** | L0–L3; **денежная L4** |
| **Формула / драйвер (рычаг)** | как метрика считается, какой рычаг двигает; в живой модели — изменишь вход, пересчёт вверх. | L0–L3; денежная L4 |
| **Источник + дата** | провенанс фактов-премиум (O*NET/ESCO/hh.ru/книга/созвон/docs). | где есть факт-премиум |
| **Контрольная точка / DoD** | критерий готовности; для линейного процесса — какая из трёх контрольных точек (поступление часа на «склад» → продажа готовой продукции → инкассация/оплата). | **Все, включая L4** |
| **Такт обзора план/факт** | DemoDay (1-й вторник месяца) / недельный спринт / по событию. | L0–L3 |
| **Стадия** | «нужно сейчас» (до вебинара 4 июля) / «при масштабе» / «избыточно». | Все |

**Минимум для неденежной L4:** `card_id`, Название, Родитель, Статус, Контрольная точка/DoD. **Измеримость L4 сохраняется через DoD: контрольная точка = бинарная метрика «выполнено / нет».** Инвариант измеримости не отменяется — он реализуется через DoD. Денежная L4 несёт ещё Поток и Метрику.

«Стадия» (готовность строить) и «Статус» (положение в потоке работы) — **разные оси**, не дублируют друг друга. По умолчанию строится то, что «нужно сейчас»; «В работе» + «при масштабе» — только осознанное решение.

## 4. Словарь статусов, сигналов и светофоров

### Статусы (канбан-колонки борта)
`Бэклог` → `Нужно сейчас` → `В работе (WIP)` → `В очереди на узкое место` → `На экспертной проверке (этап 5 — узкое место)` → `Правки` → `Готово (DoD)` → `Заблокировано (регулятор/ставка)` → `При масштабе (отложено)` → `Избыточно (не строим)`.

**WIP-лимит** на колонке «На экспертной проверке» — закон Литтла: `throughput = WIP / время в системе`.

### PDCA (для операционного контура — честный перевод цикла Федоренко вместо to do/doing/done)
`План` → `Делание` → `Контроль` → `Анализ` → новый `План`. Сверяется на DemoDay (поле «Такт обзора»).

### Сигналы V4.1
- **Слабый** (запрещён как основание решения): «кажется медленно», «вроде ок».
- **Сильный** (обязателен на бортах исполнения и узкого места): **WIP** (число единиц в системе), **90-й перцентиль времени ожидания**, **доля правок после выдачи отчёта**, **throughput** (пропускная способность).
- **Сигнал узкого места:** очередь на экспертную проверку растёт быстрее пропускной / 90-й перцентиль превышает порог → борт-сигнализатор требует вмешательства. Прямая речь Макса: «чтобы был некий борт, который бы сигнализировал в таких ситуациях, он фундаментальный».

### Светофоры финметрик (логика фиксирована, пороги — слот `[ввод Макса]`)
- **Золотое правило:** спред (ROI − стоимость капитала) > 0 → 🟢; ≈ 0 с планом выхода → 🟡; ROI < СК длительно → 🔴 (экзистенциальный риск). **MainExperts сейчас в убытках («мы сейчас в убытках, но выкарабкиваемся») — борт честно показывает 🔴/🟡 с планом выхода, не маскирует.**
- **Кассовый разрыв:** остаток покрывает ближайшие обязательства → 🟢; разрыв → 🔴 (+ сумма дефицита). Обязательства сейчас: зарплата, серверы, Anthropic.
- **Принцип соответствия:** внеоборотный актив (платформа на Rust как нематериальный актив) профинансирован краткосрочными деньгами → 🔴.
- **Финансовый рычаг:** спред (ROTA − ставка по кредиту) > 0 → рычаг допустим; < 0 (текущее состояние при убытке) → наращивать долг опасно → 🔴.
- **Сбалансированный рост (критерий 14.4):** коэффициент баланса ≈ 1 → 🟢; перегрев роста / нехватка финансирования → 🔴. **При убытке нераспределённой прибыли нет → органический сбалансированный рост ≈ 0; рост на внешних деньгах — риск, борт обязан это показывать.**

### Качество (теория ограничений / 6σ)
- **Жёсткие vs мягкие ограничения** (доля мягких — цель повышать; «жёсткое: только пятница 15–16, только Василий Петрович → мягкое: любое время, любой эксперт того же класса/качества `[критерий — ввод Макса]`»). Доля мягких = метрика **ликвидности решения** (minimax).
- **Перцентили 90/10** с удалением аутлайнеров («убрал фанатов, убрал кого бесит → достоверная оценка»).
- **Сигма-уровень** как разрешение достоверности: 1σ = 68% → 3σ = 97.7% → 6σ ≈ 3–4 дефекта/млн («пиксели с большим разрешением»).
- **Критика на борте:** 6σ на старте недостижим и избыточен для ручной экспертной проверки → по правилу стадии это «при масштабе». На запуск достаточно наблюдаемости: **доля правок + срок проверки**.
- **DMAIC** `(метод из инструментария канона docs/04; на созвоне Макс назвал только 6σ/дефект на миллион — рабочая надстройка, не прямая речь)`.

### Метки риска (в поле «Регулирующее воздействие»)
`⚠ СТАВКА` — гипотеза скрининга; `🔴 РЕГУЛЯТОР` — НПА/лицензия/данные детей; `⛔ УЗКОЕ МЕСТО` — экспертная проверка этапа 5.

## 6. Борты верхнего уровня

### 6.1. Финансовый борт

> `card_id: L1-FIN` · parent: `L0` · Путь V4.1 — «деньги» (ровно один) · Разрез Федоренко — «финансы» · Ответственный — founder (Макс) + methodology (Вадим); валидатор бенчмарков L0 — Илья · stream_scope — **оба потока раздельно + сводный только на L0** · Стадия: P&L / cash flow / безубыточность — «нужно сейчас»; ROTA/ROE/рычаг/рост 14.4 — «при масштабе».
>
> Несущий принцип борта (жёсткое правило §3.1–3.2): любой денежный объект существует в двух экземплярах — Поток 1 (HNW, люкс: высокая маржа, низкая оборачиваемость) и Поток 2 (воронка, масс: низкая маржа, высокая оборачиваемость). Сведение в одну цифру допускается ТОЛЬКО на L0 и помечается «агрегат». Без расщепления ROTA и contribution margin смешивают high-touch и self-serve — цифра становится ложью. **Текущее состояние компании — убыток (Макс: «мы сейчас в убытках, выкарабкиваемся»); борт показывает это честно 🔴/🟡 с планом выхода, не маскирует.**

## §6.1. L0-контур (макро) — карта объектов

`card_id: L0` · parent: `—` · Поток: **сводный (агрегат, помечен)** · Путь: деньги · Разрез: финансы · Ответственный: founder (Макс) + валидатор бенчмарков Илья.

Корневая карточка всей компании — **спред `ROI − стоимость капитала`** (золотое правило: «если ROI ниже стоимости капитала длительно — у компании нет будущего»). Единый светофор системы. Все денежные рёбра нижних бортов сходятся сюда — но раздельно по потокам, агрегируются только на этом ярусе.

| Объект L0 | Что держит | Формула / связь | Светофор (логика; пороги — `[ввод Макса/Илья]`) |
|---|---|---|---|
| **Золотое правило** | спред ROI − СК — корневой светофор | `спред = ROI − стоимость капитала` | >0 🟢 / ≈0 с планом выхода 🟡 / <0 длительно 🔴 (экзистенциальный риск). **Сейчас убыток → честный 🔴/🟡** |
| **Финансовый треугольник** | рёбра пересчёта живой модели: поток → рост → активы → прибыль | замкнутый контур; изменение входа на любом уровне катится вверх | n/a (каркас пересчёта, не светофор) |
| **P&L (ОПУ)** | выручка → EBITDA → EBIT → чистая, **раздельно по потокам** | `EBITDA = выручка − переменные − постоянные (до A&D)`; статья «маркетинг» питается ДРР с `L1-M` | убыток на чистой строке → 🔴/🟡 |
| **Баланс** | внеоборотные (платформа на Rust — нематериальный актив) / оборотные; собственный / срочный капитал | принцип соответствия: внеоборотный актив профинансирован краткосрочными деньгами → 🔴 | 🔴 при нарушении принципа соответствия |
| **Cash flow / кассовый разрыв** | остаток vs ближайшие обязательства; runway (личный показатель Макса) | разрыв = поступления − выплаты во времени; питается циклом оборотного капитала `L2-FIN-WC` | покрывает обязательства 🟢 / разрыв 🔴 (+ сумма дефицита) |
| **ROTA / ROE / ROI** | пирамида DuPont: ROA = рентабельность реализации × оборачиваемость активов | `ROA = (приб./выручка) × (выручка/активы)`; `ROE = ROA × рычаг`; **раздельно по потокам** | при масштабе; на старте — наблюдаемость |
| **Финансовый рычаг и устойчивость** | спред (ROTA − ставка по кредиту) | `эффект рычага = (ROTA − ставка)% × (долг/капитал)` | спред >0 → рычаг допустим; **спред <0 (текущее, при убытке) → наращивать долг опасно 🔴** |
| **Сбалансированный рост (14.4)** | детализируется в `L2-FIN-GR` | см. §6.4 | при убытке нераспред. прибыли нет → органический рост ≈ 0 🔴 |
| **Три горизонта целей** | $1 млн → 100 млн → миллиард («миллион — промежуточная цель»; борт сразу под старший горизонт) | $1 млн расщеплён по потокам (см. §6.3), иначе невалиден | n/a |

**Пересчёт макро↔микро (две оси, обязательны):**
- *Через прибыль:* CM по продукту (L4/L3) → рентабельность реализации (L1) → ×оборачиваемость = ROA → ROTA/ROE/ROI (L0) → спред ROI−СК.
- *Через ликвидность:* дни WIP (L1, цикл) порождены узким местом (экспертная проверка отчёта, этап 5) → удлиняют цикл оборотного капитала → бьют в кассовый разрыв L0.

## §6.2. Подузел L2-FIN-WC — борт оборотного капитала и ликвидности

`card_id: L2-FIN-WC` · parent: `L1-FIN` · Поток: **оба раздельно** · Путь: деньги · Разрез: финансы · Ответственный: payments (Даниил) + operations (Александр) по фактам цикла.

**Назначение.** Держать цикл оборотного капитала как линейную цепочку с тремя контрольными точками и сигнализировать кассовый разрыв. Узкое место (этап 5) материализуется здесь через «дни запасов/WIP».

### Конечный автомат cash-цикла (атрибут единицы работы, не отдельный ярус)

`деньги → счета к оплате (КЗ) → запасы/WIP → готовая продукция → счета к получению (ДЗ) → деньги`

- **«Склад» = доступные человеко-часы экспертов** (конкретный час конкретного эксперта в рамках его компетенции — «продать может только IELTS или только то-то»).
- **Запасы/WIP = «выложили календарь как готовую продукцию»**: сколько дней нужно, чтобы закрыть всем экспертам их часы под спрос.
- Единица мощности — человеко-час эксперта.

### Дни цикла и разрыв

| Метрика | Формула | Значение | Светофор |
|---|---|---|---|
| Дни запасов/WIP (Inventory Days) | `запасы(WIP) / себест. реализации × период` | `[ввод Александра/Даниила]` — порождается этапом 5 | растёт быстрее throughput → 🔴 |
| Дни дебиторки (Debtors Days / DSO) | `ДЗ / выручка × период` | `[ввод Даниила]`; при предоплате на цель → ≈ 0 | DSO↓ → 🟢 |
| Дни кредиторки (Creditors Days / DPO) | `КЗ / закупки × период` | `[ввод Даниила]`; **сюда же ложится оплата эксперту** (см. КТ ниже) | DPO↑ (в пределах договорённостей) → 🟢 |
| **Кассовый разрыв (cash gap)** | `Inventory Days + Debtors Days − Creditors Days` | **~59 дней — `(пример книги/созвона; факт MainExperts — [ввод Даниила/Александра])`**; сопутствующая кредиторка **~26 дней — тот же статус примера** | разрыв >0 → 🔴 (+ сумма дефицита) |
| Коэффициент текущей ликвидности (Current Ratio) | `оборотные активы / краткосрочные обязательства` | `[ввод Даниила]` | <1 → 🔴; ≥1 → 🟡/🟢 |

**Рычаг сокращения разрыва (созвон):** предоплата НА ЦЕЛЬ/ЗАДАЧУ (не на эксперта) обнуляет/сокращает Debtors Days; «всё, что отодвигаем после хотя бы на 12 дней — прекрасно»; при предоплате цикл может уйти в минус (−12 дней — `[иллюстрация механики, не факт]`). Личный кейс Макса как обоснование инварианта: на массовом рынке без доверия оплата постфактум растягивается до 365–700 дней → дебиторка убивает ликвидность → на масс-рынке берём вперёд (аналогия такси/отель — заморозка с карты).

### Три контрольные точки (конечный автомат — единое определение по всей системе)

> **Несущая правка контракта.** Два денежных события РАЗВЕДЕНЫ явно, чтобы конечный автомат был однозначен при импорте. КТ-3 — это инкассация С КЛИЕНТА. Оплата эксперту — отдельное событие цикла, влияющее на Creditors Days (DPO), и НЕ является КТ-3.

| Точка | Событие | Привязка к циклу | На каком состоянии операционки (L1-OPS) |
|---|---|---|---|
| **КТ-1** | поступление часа эксперта на «склад» (час встал в календарь как запас) | вход запасов/WIP | поиск / матч (час доступен) |
| **КТ-2** | продажа готовой продукции потребителю (отчёт/услуга проданы) | запасы → ДЗ | исполнение / выдача |
| **КТ-3** | **ИНКАССАЦИЯ С КЛИЕНТА** (деньги получены от клиента) | ДЗ → деньги; обнуляет Debtors Days | **состояние 2 «предоплата на цель получена»** — при предоплате на цель КТ-3 наступает ДО КТ-2 (DSO→0) |
| *(не КТ — отдельное событие)* | **ОПЛАТА ЭКСПЕРТУ** | влияет на Creditors Days (DPO), отодвигает/удлиняет кредиторку | состояние 8 «оплата эксперту» в конце цепочки |

**Согласование по системе (инвариант КТ-3):** определение КТ-3 = инкассация с клиента — едино в `L2-FIN-WC` (здесь), в карточке единицы работы `L3-BTL-01` (§2) и в операционном борте `L1-OPS`. В `L1-OPS` состояние 8 несёт привязку «оплата эксперту → Creditors Days» (НЕ КТ-3); КТ-3 проставлена на состоянии 2 «предоплата получена». Так при предоплате на цель КТ-3 законно наступает раньше КТ-2 (Debtors Days ≈ 0), а оплата эксперту в хвосте цепочки не путается с инкассацией и работает на DPO.

## §6.4. Подузел L2-FIN-GR — борт сбалансированного роста (14.4)

`card_id: L2-FIN-GR` · parent: `L1-FIN` · Поток: **оба раздельно** · Путь: деньги · Разрез: финансы · Ответственный: founder (Макс) + валидатор Илья. **Стадия — «при масштабе».**

| Рычаг | Метрика | Драйвер балансировки | Светофор |
|---|---|---|---|
| Темп роста выручки | `(выручка_t − выручка_{t−1}) / выручка_{t−1}` | сокращение роста до устойчивого (пример: до 3% / до 10%) | перегрев → 🔴 |
| Доля нераспределённой прибыли | `нераспред. прибыль / выручка` | повышение доли (пример: до 5–10%) | при убытке = 0 → 🔴 |
| Оборотные активы / выручка | `оборотные активы / выручка` | снижение отношения | рост отношения → 🔴 |

**Коэффициент сбалансированного роста ≈ 1 → 🟢; перегрев / нехватка финансирования → 🔴.**

> *Критика на борте (жёстко):* при текущем убытке нераспределённой прибыли нет → **органический сбалансированный рост ≈ 0**. Рост возможен только на внешних деньгах — а при отрицательном спреде рычага (ROTA < ставки по кредиту, §6.1) это прямой риск. Борт обязан показывать 🔴, а не рисовать здоровый рост. Рост считать РАЗДЕЛЬНО по потокам: у Потока 1 (люкс) и Потока 2 (масс) разные оборачиваемость и маржа — общий коэффициент сбалансированности был бы фиктивным. Аналогия Макса: «порвёшь мышцу несбалансированным ростом — будет долго заживать».

## §6 — Критика (в теле борта, не в сноске)

1. **Расщепление выручки по двум потокам — несущее.** Без раздельных таблиц ROTA и CM смешивают люкс (Поток 1: высокая маржа, низкая оборачиваемость, канал — нетворкинг) и масс (Поток 2: низкая маржа, высокий оборот, канал — воронка). Любая сводная маржа без расщепления — «ошибка средних». Сведение только на L0 и только с пометкой «агрегат».
2. **Текущая убыточность — честно 🔴/🟡.** Спред ROI−СК отрицателен → 🔴 экзистенциального риска с планом выхода. Не маскировать. Из убытка следуют: нераспределённой прибыли нет → сбалансированный рост ≈ 0; спред рычага <0 → наращивать долг опасно.
3. **Цель $1 млн невалидна без расщепления (§3.2).** Вороночная прикидка масштабирования отнесена к ПРАВИЛЬНОМУ потоку: $1 млн ≈ 80–90 млн ₽ ≈ ~1700 оплат Профориентации по 50 000 ₽ (живая цена CTA Потока 2, флоу 18.06, `docs/01 стр.25`, `docs/02 стр.36`) ≈ 9–10 проверок/день — упирается в ручную проверку (`docs/01 стр.39`, противоречие №1). Это противоречие ВОРОНКИ (Поток 2), оно живёт на `L2-BTL-01`, а не как «старая номенклатура Потока 1». 50К-лесенка Потока 1 — отдельный объект с тем же числом (§6.3), не сливать и не вычитать.
4. **КТ-3 однозначна по всей системе.** Инкассация с клиента = КТ-3; оплата эксперту — отдельное событие на DPO. Конечный автомат cash-цикла не двоится при импорте.

### 6.2. Развязка денежных событий цикла (три контрольные точки — одно определение во всей системе)

Конечный автомат трёх контрольных точек (атрибут карточки, §4) требует однозначности. Два денежных события разнесены явно, чтобы КТ-3 не получала двух смыслов:

| Событие цикла | Контрольная точка | На что влияет | Поведение при предоплате на цель |
|---|---|---|---|
| Поступление часа эксперта на «склад» | **КТ-1** | формирование WIP/запасов | — |
| Продажа готовой продукции (закрытие сделки) | **КТ-2** | признание выручки | — |
| **Инкассация с клиента** | **КТ-3** | **Debtors Days (DSO)** | предоплата на цель → КТ-3 наступает **ДО КТ-2** → **Debtors Days ≈ 0** (цикл может стать отрицательным) |
| **Оплата эксперту** | **НЕ КТ-3** (отдельное событие) | **Creditors Days (DPO)** | независимо; влияет на кредиторскую часть цикла |

> **Инвариант (согласован с `L3-BTL-01` §2 и `L2-FIN-WC` §6.2).** КТ-3 = **инкассация с клиента**; при предоплате НА ЗАДАЧУ (не на эксперта) КТ-3 наступает раньше КТ-2 и **обнуляет Debtors Days** (личный кейс Макса: оплата на массовом рынке без доверия растягивается на 365–700 дней — предоплата на задачу это снимает). **Оплата эксперту — отдельное событие, влияет на Creditors Days (DPO), и КТ-3 НЕ является.** Прежняя жёсткая привязка КТ-3 к «инкассации/оплате эксперту в конце цепочки» снята: на состоянии 8 остаётся только «оплата эксперту → Creditors Days», а КТ-3 проставлена на состоянии 2 (предоплата получена).

### 6.4. Подузел качества `L2-OPS-Q` (DMAIC / 6σ)

`card_id`: `L2-OPS-Q` · `parent_id`: `L1-OPS` · путь: исполнение (делегирование) · стадия: наблюдаемость — нужно сейчас; 6σ — при масштабе.

> **DMAIC — метод из инструментария канона `docs/04`, не прямая речь Макса.** На созвоне 26.06 Макс назвал только «6σ / дефект на миллион»; Define–Measure–Analyze–Improve–Control — законная надстройка канона, помечена как метод, не как цитата.

| Поле | Содержание |
|---|---|
| **Колонки борта (DMAIC)** | **Define** (что считаем дефектом — правка после выдачи) → **Measure** (доля правок; срок экспертной проверки) → **Analyze** (перцентили 90/10 с удалением аутлайнеров: «убрал фанатов, убрал кого бесит → достоверная оценка») → **Improve** (жёсткие → мягкие ограничения; рычаги срока проверки) → **Control** (удержание уровня сигма) |

На запуск достаточно **наблюдаемости** (доля правок + срок проверки). Оптимизация только под срок запрещена — триада результативность + эффективность + качество |

## 7.2. Ось «через прибыль» (пересчёт снизу вверх до спреда ROI−СК на L0)

Старт — карточка `L4-FIN-CM-01-01` (contribution margin на человеко-час эксперта). Стрелки пересчёта реальные, числа `[иллюстрация]`.

**Шаг 1. Contribution margin на отчёт (юнит-экономика, Поток 2):**
```
CM/отчёт = выручка по отчёту − переменные затраты
         = 9 990 − 3 500 = 6 490 ₽           [иллюстрация]
```

**Шаг 2. CM на человеко-час эксперта (единица мощности = человеко-час):**
```
CM/час = CM/отчёт ÷ человеко-часы эксперта на отчёт
       = 6 490 ₽ ÷ 2 ч = 3 245 ₽/час         [иллюстрация]
```
Это прямо измеряет **цену узкого места**:
```
цена узкого места = CM/час × длина очереди на этапе 5
                  = 3 245 ₽/час × 8 отчётов(×2ч) ≈ 51 920 ₽ замороженного вклада в очереди   [иллюстрация]
```

**Шаг 3. CM → рентабельность реализации (агрегат L1, Поток 2):**
Сумма CM по всем отчётам за период − постоянные затраты = операционная прибыль; делим на выручку:
```
рентабельность реализации = операционная прибыль ÷ выручка
                          = 14 %                  [иллюстрация — пример книги, не факт MainExperts]
```

**Шаг 4. ROA = рентабельность × оборачиваемость (разложение DuPont):**
```
ROA = рентабельность реализации × оборачиваемость совокупных активов
    = 14 % × 1,3 = 18,2 %                          [иллюстрация]
```

**Шаг 5. ROA → ROTA → ROE/ROI:**
```
ROTA (доходность совокупных активов до процентов) ← из ROA, очищенной структурой активов
ROI ← с учётом инвестированного капитала
                                                    [числа — ввод Макса/Ильи, бенчмарки с провенансом]
```

**Шаг 6. Спред ROI − стоимость капитала (корневой светофор L0):**
```
спред = ROI − СК
если спред > 0 → 🟢; ≈ 0 с планом выхода → 🟡; ROI < СК длительно → 🔴 (экзистенциальный риск)
```
> MainExperts сейчас в убытке — борт честно показывает 🔴/🟡 с планом выхода, не маскирует (§6 светофоры). Рычаг пересчёта: подъём CM/час на L4 (цена ↑ или переменные затраты / часы эксперта ↓) поднимает рентабельность → ROA → спред. Так карточка человеко-часа эксперта прослеживается до корневого светофора компании.

**Цепочка card_id по оси прибыли:** `L4-FIN-CM-01-01` → `L1-BTL`/`L1-FIN` (рентабельность) → ROA → `L0` (спред ROI−СК).

## 7.3. Ось «через ликвидность» (пересчёт до кассового разрыва на L0)

**Шаг 1. Дни WIP (порождаются узким местом — этап 5, `L1-BTL`):**
```
дни WIP = время единицы работы в системе (закон Литтла: throughput = WIP / время в системе)
при очереди 8 отчётов и пропускной 9–10/день  →  WIP-задержка ≈ N_wip дней   [иллюстрация]
```

**Шаг 2. Дни WIP → цикл оборотного капитала (`L2-FIN-WC`):**
```
цикл = дни запасов/WIP + Debtors Days (DSO) − Creditors Days (DPO)
```
Берём пример книги/созвона `(факт MainExperts — [ввод Даниила/Александра])`: разрыв ~59 дней, кредиторка ~26.

**Шаг 3. Эффект предоплаты на цель (инвариант ликвидности, §3.11):**

Здесь работают **три контрольные точки cash-цикла** — и разнесены два разных денежных события (см. правку КТ-3 ниже):
- **КТ-1** — поступление часа эксперта на «склад» (готовность мощности).
- **КТ-2** — продажа готовой продукции (отчёт выдан / календарь продан).
- **КТ-3 = ИНКАССАЦИЯ С КЛИЕНТА.** При предоплате на цель КТ-3 наступает **до КТ-2** → Debtors Days (DSO) → 0.
- **Оплата эксперту — отдельное событие цикла (НЕ КТ-3):** влияет на Creditors Days (DPO), сдвигает кредиторку вперёд.

```
БЕЗ предоплаты:  DSO = 30 дней (N)  →  цикл ≈ 59 дней   [иллюстрация на примере книги]
ПРИ предоплате на цель: КТ-3 (инкассация) до КТ-2 → DSO → 0
                        и оплата эксперту (DPO) отодвинута хотя бы на 12 дней
                        →  цикл может стать отрицательным (≈ −12 дней)   [иллюстрация]
```

**Шаг 4. Цикл → кассовый разрыв (L0):**
```
кассовый разрыв: остаток покрывает ближайшие обязательства → 🟢; разрыв → 🔴 (+ сумма дефицита)
```
> Рычаг пересчёта по ликвидности: предоплата на цель обнуляет Debtors Days (КТ-3 до КТ-2), а отодвинутая оплата эксперту (DPO) удлиняет кредиторку — цикл сжимается или уходит в минус, кассовый разрыв на L0 закрывается. Узкое место материализуется как финансовый показатель: рост очереди на этапе 5 удлиняет дни WIP → удлиняет цикл → бьёт в кассовый разрыв.

**Цепочка card_id по оси ликвидности:** `L1-BTL` (дни WIP) → `L2-FIN-WC` (цикл) → `L0` (кассовый разрыв). Предоплата на цель: `L1-OPS` (состояние 2, КТ-3/инкассация) → обнуляет Debtors Days в `L2-FIN-WC`.

## 8. Карта связей бортов

| Ребро (откуда → куда) | Переток / механика |
|---|---|
| `L1-M` → `L1-FIN` | ДРР питает статью «маркетинг» в P&L → влияет на рентабельность реализации. ДРР ≈ обратная к ROI рекламы («чем меньше, тем лучше»); это переменный расход, а не вся структура. |

| `L1-PRD` → `L1-FIN` (узел `L2-FIN-CM`) | Часы (массово/дорого) vs функции-модули (оцифровано/дёшево/масштабируемо) → две разные юнит-экономики CM → **НЕ совпадают с двумя потоками 1:1** (часы продаёт и Поток 1, и эксперты Потока 2; expert-hour разносить по каналу продажи). |

## 9. Минимальный комплект «нужно сейчас»

Правило стадии (Федоренко): «нужно сейчас» — до запуска трафика и первого вебинара; «при масштабе» — после повторяемой выручки; «избыточно» — не строим.

### НУЖНО СЕЙЧАС (строим до 4 июля)
1. **`L1-FIN` — минимальный финансовый борт:** P&L план/факт (раздельно по потокам), cash flow / кассовый разрыв (🟢/🔴 + сумма дефицита, обязательства = зарплата/серверы/Anthropic), точка безубыточности по каждому продукту/потоку. Показывать убыток честно 🔴/🟡 с планом выхода, не маскировать.
2. **`L1-M` — маркетинговый ДРР-борт (Поток 2):** три под-таблицы — атрибуция контента (статья × слова × тема → продажи / ДРР), план/факт ассортимент × канал, воронка вебинара `⚠ СТАВКА` на конверсии скрининг→покупка. Это артефакт, ради которого Макс звал Игоря.
3. **`L1-BTL` — наблюдаемость узкого места:** WIP, 90-й перцентиль ожидания, доля правок, throughput (закон Литтла). Журнал событий `report_queued`/`report_reviewed`/`report_revised`. Противоречие $1 млн на виду борта.
4. **`L1-OPS` — наблюдаемость операционки/матчинга:** состояния заявка→предоплата на цель→face-control→матч/альтернатива→оплата; событие `prepay_on_goal` (обнуляет Debtors Days). Доля правок + срок проверки (наблюдаемость качества).
5. **`L1-RISK` — реестр регулирующих воздействий:** данные несовершеннолетних 10–18, бессрочное хранение, граница психодиагностики, лицензии методик BFAS/RIASEC `[рабочее название, лицензии нет]`, профили живых людей. **Стадия — «нужно сейчас», до трафика, не позже.**
6. **Журнал событий** (§5) и **схема карточки** (§3) как корпоративный стандарт — без них наблюдаемость и план/факт не операционализируются.

### 9.1 V4.1 «Петли управления ценностью»

- **Шесть путей, по одному на борт (кросс-загрязнение запрещено).** `L1-M` → клиент; `L1-OPS` → заказ; `L1-BTL` → исполнение; `L1-FIN` → деньги; `L1-RISK` → риск; `L1-PRD` → данные.
- **Разнесение «заказа» и «исполнения» — фактическое, не декларативное (правка пути L1-OPS).** Контракт `L1-OPS` помечен `"path_v41": "заказ / исполнение"` — это конфликтует с §3.9 («один борт ровно на одном пути; один борт не несёт двух путей в одной метрике»). Разрешение:
  - **Несущий путь `L1-OPS` — «заказ».** Поле «Путь V4.1» приводится к единственному значению **«заказ»** со сноской: *«точка передачи на путь „исполнение“ — после состояния „матч/альтернатива“; дальше — ребро в `L1-BTL`, не собственная метрика `L1-OPS`».*
  - Состояния `L2-OPS-MATCH` 6–7 («исполнение», «контроль качества») и любая ссылка на срок проверки этапа 5 — это **переход на путь «исполнение» с делегированием в `L1-BTL`**: оформляются ребром карты связей (§8), а НЕ собственным показателем `L1-OPS`. Этап 5 по контракту принадлежит `L1-BTL` (путь «исполнение»), и метрику его срока держит `L1-BTL`, а не операционный борт.
  - **Сквозная метрика lead time разрезается на две, по путям:**
    - **«Время заказа»** = заявка → предоплата на цель → поиск → face-control → матч. Путь «заказ». Метрика и владелец — `L1-OPS` (operations/Александр + payments/Даниил).
    - **«Время исполнения»** = исполнение → проверка этапа 5 → правки → выдача. Путь «исполнение». Метрика и владелец — `L1-BTL` (operations/Александр + methodology/Вадим).
  - Так состояния «исполнение / контроль качества / срок этапа 5» больше не сидят в одной метрике `L1-OPS` с состояниями заказа.
- **Единица работы = отчёт по клиенту** (§3.7) — общая для `L1-BTL`, `L2-BTL-01`, `L3-BTL-01`.
- **Примитивы управляемости** на каждом борте: границы (поток + путь), состояния (канбан-колонки §6), события (журнал §5/мини-таблица события), цели (слот `[ввод Макса]` по SMART), показатели (метрика план/факт), ответственные (направление + лицо), рычаги (поле «Формула / драйвер»), обратная связь (такт обзора — DemoDay), обучение (PDCA-петля эпика).
- **Уровни зрелости — строго по порядку: наблюдаемость → прогноз → рекомендации → оптимизация.** ИИ-рекомендация раньше наблюдаемости запрещена (усиливает шум). На старте все борты исполнения и узкого места стоят на «наблюдаемости»; «оптимизация / 6σ» — `при масштабе`.
- **Журнал событий обязателен** (без событий PDCA крутится на ощущениях): см. мини-таблицу схемы события §5.
- **Сильные сигналы — WIP, 90-й перцентиль времени ожидания, доля правок после выдачи** — обязательны на `L1-BTL` и `L1-OPS`; слабые сигналы («кажется медленно») запрещены как основание решения.

### 9.5 Узкое место

- Узкое место = **экспертная проверка отчёта (этап 5)**, подтверждено независимо в трёх слоях. Отдельный обязательный объект — борт `L1-BTL`, путь «исполнение», единица работы = отчёт по клиенту.
